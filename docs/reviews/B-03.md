## Verdict: CHANGES_REQUESTED

One blocker and one major. Both are in the same place: `Money.Allocate(IReadOnlyList<decimal>)` and the property test that is supposed to guard it. **`Allocate` can silently lose or invent a minor unit, and can return parts that are not whole minor units, for ordinary weights** — deterministic reproductions below, at SMB invoice scale. Everything else in the change is careful, well-reasoned work of the standard B-01 and B-02 set; `Money.Round`, `Allocate(int)`, `Currency`, `Quantity`, `Percentage`, `DateRange`, the identifiers and `Result` all held up to everything I tried.

The fix is contained (one method plus one generator) and does not disturb the rest of the design.

The author's reported probes are honest and understated (7 failures, not 2). The two gaps are in the assembly-purity pair, not the value objects.

**`default(T)` — all four claims hold.** `default(Money)` throws on `+`, unary `-`, `Round`, `Allocate` and every comparison, naming `default(Money)` as the cause. `default(Quantity)` likewise, including `* Money`. `default(DateRange)` is empty: `IsEmpty` true, `Days` 0, `Contains` false, `Overlaps` false, `Intersect` null, `LastDay` throws. `default(Result)` and `default(Result<T>)` read as failures carrying `Error.Unassigned`, and `Value` throws. `default(RoundingPolicy)` refuses to round rather than inheriting a framework default. One narrow exception: m-2.

**`DateRange`.** The empty-range fix in `Overlaps` (`DateRange.cs:126-130`) is correct and complete. `Intersect` delegates to `Overlaps` and inherits it; `Contains` is naturally correct for an empty range; `LastDay` refuses rather than returning the day before the start. I could not construct an input where the four disagree.

**The EF Core forward-compatibility test (`EntityIdContract.cs:88-102`).** It de-risks a real trap and is worth keeping: written the obvious way, `Expression<Func<Guid, TId>> fromProvider = stored => TId.From(stored)` does not compile at all (an expression tree may not access a static abstract interface member), and a developer meeting that in B-05 would plausibly conclude the `IEntityId<TSelf>.From` design is unusable and write fifty per-type converters. The test records the workaround where the next reader will find it. What it does **not** prove is that EF Core *accepts* the pair — the `Invoke` node the delegate indirection introduces is fine for materialization but is not SQL-translatable. Nit n-4; the test still earns its place.

**Allocation, read against ADR-0021 §6 rather than trusted.** The algorithm is a correct largest-remainder implementation *in exact arithmetic*: `Σ floor(T·wᵢ/W) = T − (Σ rᵢ)/W`, so `leftover` is an integer in `[0, n)`; parts with a zero remainder can never be reached by the leftover loop because `leftover < |{i : rᵢ > 0}|`, which is why a zero-weighted part takes nothing; the comparer is a total order, so the sort is deterministic regardless of stability; the magnitude is split and the sign re-applied at `Money.cs:325-331`, so a credit note splits exactly like the invoice it reverses — confirmed numerically: `−100.00` over 3 gives `−33.34, −33.33, −33.33`.

**The author's `decimal %` reasoning is right in principle, and the digit it turns on survives.** With weights `[1, 1.000000000000000000000001, 1]` the ordering turns on the 24th decimal place and the implementation gives the cent to part 1 — the mathematically correct part. A key computed by a rounding division would have tied and given it to part 0. The remainder key *is* exact.

**But the value the key is computed from is not.** That is the blocker.

## Findings

### Blocker

**B-1 — `Money.Allocate(IReadOnlyList<decimal>)` silently loses or invents minor units, and returns parts that are not whole minor units**
`src/Aurora.SharedKernel/Money.cs:305-318`, doc claim at `:265-269`, promise at `:252-257`

`decimal` multiplication and division are exact only while the result fits in 28–29 significant digits; beyond that they round, silently, without an exception. At `Money.cs:310` the code computes `share = totalMinorUnits * weights[part]`. A weight produced by a `decimal / decimal` division carries **28 decimal places**, so for a total with more than one or two significant minor-unit digits this product is rounded before `%` ever sees it. `share % weightTotal` is then an exact remainder of an inexact `share`, and `(share - remainder) / weightTotal` is no longer an integer. Two failures follow:

1. `partMinorUnits[part]` is not a whole number of minor units, so the returned parts are amounts nobody can pay — the method's own input precondition (`IsInWholeMinorUnits`) is violated by its output.
2. `claimed` is not integral, so `int leftover = (int)(totalMinorUnits - claimed)` at `:318` **truncates** — `0.9999999999999999999999999` becomes `0` — and a whole minor unit disappears. `Σ parts ≠ total`, which is the one law ADR-0021 §6 exists to guarantee.

Deterministic reproductions, run against this branch's build:

```csharp
// (a) SMB scale: a $3,914.33 discount apportioned over three lines by amount ratios.
//     One cent vanishes. No exception, no warning.
new Money(3914.33m, Nzd).Allocate([5851.58m / 9400.65m, 2480.8m / 3508.02m, 7205.35m / 2643.21m])
// => sum = 3914.32  (total = 3914.33)

// (b) The simplest allocation there is: one line, weight one third.
new Money(6252019.19m, Nzd).Allocate([1m / 3m])
// => [6252019.1900000000000000000001]   IsInWholeMinorUnits == false

// (c) Four ordinary ratio weights. One cent short.
new Money(7810283.36m, Nzd).Allocate(
    [9649.37m / 9055.42m, 6827.95m / 6769.69m, 1774.05m / 5469.35m, 4729.04m / 9735.47m])
// => sum = 7810283.35
```

Not an exotic input class. Weights are documented at `Money.cs:262-264` as proportions whose "unit and scale do not matter", and the most natural way for a caller to produce them is exactly `lineAmount / documentTotal`. I ran 300,000 randomised splits with weights of that form (totals up to ten million, one to five parts): **61,801 — 20.6% — did not sum exactly to the total.** Most differ by sub-cent dust that makes the parts unpayable and that `numeric(19,4)` will later round away in a direction nobody chose; a minority lose or invent a whole minor unit. At SMB magnitudes (totals under $10,000) the whole-cent losses still occur.

The consequence is precisely what ADR-0021 was written to prevent: an invoice whose lines do not add up to its total, with no `RoundingAmount` to explain the difference, no tolerance check to fail the posting, and nothing in the code path that could notice.

`Allocate(int parts)` (`Money.cs:236-243`) is **not** affected — its weights are all `1m`, every product is exact, and it is correct for any total decimal can hold. The defect is confined to the weighted overload.

The documentation at `Money.cs:266-268` makes this worse rather than better:

> *"Weights meet the amount at full `decimal` precision, so weights of extreme magnitude can exhaust it. That surfaces as `OverflowException` from `decimal` itself rather than as a quietly wrong split."*

`OverflowException` is what happens when the *magnitude* leaves decimal's range. Exhausting the *significand* — the case that actually bites — produces exactly the quietly wrong split the sentence promises cannot happen. This is the B-01 pattern on the most dangerous method in the change: a comment that tells the next reader to stop looking.

**Fix.** The arithmetic must not depend on the precision of the weights. Three parts, all required:

1. **Make the split exact by construction.** Weights are proportions, so scale them to integers once and do the whole largest-remainder computation in integers. `System.Numerics.BigInteger` is BCL, tier-0 legal, and removes the precision budget rather than moving it:

   ```csharp
   int scale = weights.Max(w => w.Scale);                    // decimal.Scale, BCL
   BigInteger[] w = [.. weights.Select(x => Scaled(x, scale))];
   BigInteger weightTotal = w.Aggregate(BigInteger.Zero, static (a, b) => a + b);
   BigInteger total = Scaled(Math.Abs(Amount) * MinorUnitScale(Currency), 0);
   // per part: BigInteger q = BigInteger.DivRem(total * w[i], weightTotal, out BigInteger r);
   ```

   Every part is an integer count of minor units by construction, `leftover` is exact, and no input can round. This method is worth being boring in.
2. **Verify the postcondition before returning.** Assert that every part is integral, that `leftover ∈ [0, weights.Count)`, and that `Σ parts == total` — and throw naming the weights if not. A method whose single law is "the parts add up" must not be the one method in this assembly that can be quietly wrong. Related: `(int)(...)` at `:318` is a truncating cast of a value the code believes is already an integer; after the fix it should be an exact conversion that cannot swallow a fraction.
3. **Correct the two claims.** `Money.cs:266-268` and `src/Aurora.SharedKernel/README.md:38-40` both assert the property that is currently false.

### Major

**M-1 — The property test ADR-0021 §6 asks for by name cannot express the failure class, because its weight generator is ten hand-picked literals**
`tests/unit/Aurora.SharedKernel.UnitTests/MoneyAllocationPropertyTests.cs:119-120`

```csharp
private static Gen<decimal> Weights() =>
    Gen.Elements(0m, 0m, 0.25m, 0.5m, 1m, 2m, 3m, 5m, 7m, 12.5m);
```

Every one has at most two decimal places, so `totalMinorUnits * weight` is always exact and the property can never fail for the reason that matters. ADR-0021 §6 asks for `sum(parts) == total` "**for arbitrary inputs** and arbitrary part counts". The total, the currency and the part count are genuinely arbitrary here — the weights are an enumeration. A generator drawing weights as `decimal / decimal` ratios found counterexamples within seconds.

This is the B-02 pattern applied to a generator: the check reports green and cannot report that it never visited the region where the law breaks. It is major separately from B-1 because fixing the arithmetic without widening the generator leaves the same blind spot for the next person who touches the method.

**Fix.** Widen `Weights()` so the weight dimension is actually arbitrary: weights produced by `decimal` division (28 decimal places), high scale, wildly mixed magnitude, and single-weight allocations. Keep the zero weights. Add the three reproductions in B-1 as example regressions, and add one more property that would have caught this on its own:

```
Allocate([w]).Single() == total   for every positive weight w
```

Assert `IsInWholeMinorUnits` on every returned part in the example tests too.

### Minor (candidate follow-ups, not blocking)

**m-1 — `No_floating_point_type_appears_anywhere_in_the_kernel` only sees signatures; a `double` in a method body passes.**
`tests/unit/Aurora.SharedKernel.UnitTests/SharedKernelAssemblyTests.cs:31-39,61-103`. Reflection over fields, properties, parameters and return types cannot see locals. This stayed green:

```csharp
public static decimal DiscountedTotal(decimal amount, int percentOff)
{
    double factor = 1.0 - (percentOff / 100.0);
    return (decimal)((double)amount * factor);
}
```

A `(double)` cast of a monetary `decimal` is the exact violation the rule exists to stop, and the test name, the class doc-comment, `Aurora.SharedKernel.csproj:8-11` and `README.md:3-7` all assert the stronger property. **Fix:** either narrow the four claims to "no floating-point type appears in any member signature", or close the gap — `method.GetMethodBody()?.LocalVariables` is reachable through the same reflection. B-04 owns the authoritative solution-wide rule; whichever is chosen, the claim and the mechanism must say the same thing.

**m-2 — `Money.IsZero`/`IsPositive`/`IsNegative` answer for a `default(Money)` instead of refusing.**
`src/Aurora.SharedKernel/Money.cs:66,69,72`; identically `Quantity.cs:56,59,62`. `default(Money).IsZero` is `true`. Every other member refuses a currency-less amount. These three are the one place where an amount naming no currency passes for a valid zero, so `if (discount.IsZero) return total;` silently skips an unassigned field instead of throwing — the type's own thesis inverted, in the shape that produces no stack trace. **Fix:** call `AssertSpecified()` in the three predicates and add the case to the default-value tests for both types. Two lines each, and this is the last cheap moment.

**m-3 — The BCL test does not see a declared-but-unused `PackageReference`.**
`SharedKernelAssemblyTests.cs:42-55`; claims at `Aurora.SharedKernel.csproj:8-11` and `README.md:9`. `Assembly.GetReferencedAssemblies()` reports what the compiler emitted, not what the project declares. An unused `<PackageReference Include="Shouldly" />` stayed green; it went red only once a type from it was used. **Fix:** either read the declared references (the committed `packages.lock.json` has them) or reword both claims to say what the test does.

**m-4 — No `Money` equivalent of `Quantity`'s default-value coverage for `*` and `/`.**
`MoneyTests.cs:113-122` covers only `+` and unary `-`; `default(Money) * 2m`, `/ 2m`, `.Abs()` and `.IsInWholeMinorUnits` are implemented correctly but untested. **Fix:** extend to match `Quantity`'s.

## Patterns noted for this codebase

**A generator is a mechanism, and a mechanism that cannot fail is not a check.** B-01's was a comment claiming behaviour no property produced; B-02's was a stage reporting PASS without a count; B-03's is a property test whose input space excludes the region where the law breaks. The shape repeats: the thing that reports green is trusted in proportion to how universal its name sounds. For every property-based test in this repository, ask *which dimension of the input is actually arbitrary, and which is a hand-written list?* — and say so in the test's own documentation.

**`decimal` is exact until it is not, and it does not tell you.** `decimal` multiplication and division round silently past 28–29 significant digits. `decimal` is exact *in base 10*, which is not the same as exact, and the digits vanish where nothing is watching. Any money algorithm in this codebase that multiplies a magnitude by a caller-supplied factor and then relies on the result being integral must either work in integers (`BigInteger` is BCL and free at tier 0) or verify its own postcondition before returning. This belongs in ADR-0021 as a consequence, because the next place it will bite is tax apportionment in ADR-0023.

**The rest of this branch is the standard to hold future kernel work to.** Every type refuses to answer a question it cannot answer honestly, every `ToString` is culture-invariant, every exception message names the cause and the fix, and the author disclosed their judgement calls instead of burying them. The blocker exists because one method had to be clever about precision, and cleverness about precision is the one thing this assembly should never be.
