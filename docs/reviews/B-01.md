## What I verified empirically (the expensive-to-reverse settings)

These are the things the brief asked me to weigh most heavily, so I tested them rather than read them.

**The analyzer, nullable and style settings genuinely bite.** I dropped a deliberately awful file into `src/Aurora.SharedKernel/` in the scratch worktree and rebuilt. Result: **0 warnings, 16 errors** — `CS8602`/`CS8618` (nullable), `CA1822` (quality analyzers active at `latest-recommended`), `IDE0005`, `IDE0011`, `IDE0044`, `IDE0051`, `IDE0055`, `IDE1006` (style rules active via `EnforceCodeStyleInBuild`), all promoted to errors by `TreatWarningsAsErrors`. This is not a skeleton that is clean because nothing is switched on. The `GenerateDocumentationFile=true` + `NoWarn=CS1591` pairing in `Directory.Build.props:37` is the correct and non-obvious trick needed to make `IDE0005` report at build time, and the author documented why.

**The test-project relaxation works and is correctly scoped.** A probe test named `Posting_a_reversal_leaves_the_original_entry_unchanged` in a `public` class under `tests/` builds with 0 warnings — the `[tests/**/*.cs]` section at `.editorconfig:269` disables `CA1707`/`CA1515` and downgrades `IDE1006` there and nowhere else.

**Central package management is airtight.** No `Version=` attribute appears in any `.csproj`; all 42 versions live in `Directory.Packages.props`. `ManagePackageVersionsCentrally` and `CentralPackageTransitivePinningEnabled` are both on.

**Dependency direction matches §1/§2 and ADR-0006 tiering.** `SharedKernel` → nothing; `Documents.Canonical` → `SharedKernel`; `Countries.Contracts` → `SharedKernel` + `Documents.Canonical`; `Aurora.Web`/`Aurora.Worker` → `Aurora.Composition` only; `Aurora.Composition` → nothing yet. No host reaches past `Composition`. The `Modules.`/`Platform.` namespace segments are preserved and the READMEs say so explicitly.

**No unapproved direct dependency.** I parsed all nine lock files: 66 packages in the graph, **every direct `PackageReference` is listed in `dependencies.md`**, and none of the rejected packages (AutoMapper, MediatR, MassTransit, FluentAssertions, Hangfire, Duende, Redis, Moq, NetArchTest) appears anywhere in the graph. `Bogus` is correctly withheld pending its licence-file check, and `Microsoft.AspNetCore.App` is correctly reached via `<FrameworkReference>` rather than a package.

**`global.json`** pins `10.0.401` with `rollForward: latestPatch` plus `allowPrerelease: false` — sane; it accepts a patch of the installed feature band and nothing wider.

**`nuget.config`** clears inherited sources, pins nuget.org, and adds an explicit `packageSourceMapping` — better than the spec asked for, and the right supply-chain posture.

Also worth calling out as good judgement beyond the brief: `UseArtifactsOutput` (`Directory.Build.props:73`) keeps ~60 future projects from sprouting `bin/`+`obj/` pairs and lands output in the already-git-ignored `artifacts/` that §1 anticipates; and `NuGetAuditLevel=high` (`Directory.Build.props:58`) deliberately aligns the build's audit threshold with verify.sh stage 5 instead of letting `TreatWarningsAsErrors` silently impose a stricter rule in a second place. Both are explained in comments.

### Major

**M-1 — `Aurora.TestKit` aborts the test run; `dotnet test Aurora.sln` exits 1**
`tests/Aurora.TestKit/Aurora.TestKit.csproj:14-21` (and the comment at line 11)

`Aurora.TestKit` is a plain library that carries `PackageReference`s to `xunit` and `Testcontainers.PostgreSql`. `dotnet test` on the solution still hands its output assembly to VSTest, and the test host fails to start because a library's output folder does not copy its NuGet dependencies:

```
Testhost process for source(s) '.../Aurora.TestKit/release/Aurora.TestKit.dll' exited with error: Error:
  An assembly specified in the application dependencies manifest (Aurora.TestKit.deps.json) was not found:
    package: 'BouncyCastle.Cryptography', version: '2.7.0'
    path: 'lib/net6.0/BouncyCastle.Cryptography.dll'
Test Run Aborted.
```

I confirmed by isolation that this is the **sole** cause of the non-zero exit: the two real test projects reporting "No test is available" do not by themselves make `dotnet test` fail on SDK 10.

Three reasons this is major rather than minor, despite `dotnet test` being outside B-01's stated AC:

1. The csproj comment at line 11 asserts *"`dotnet test` never targets it"*. That is verifiably false, so the next developer to hit this error will not look in this file — they will chase a phantom BouncyCastle/Testcontainers problem.
2. `Aurora.TestKit` is referenced by every module integration-test project generated from B-10 and B-14. The misdiagnosis cost compounds across every future module.
3. It lands a known-red `dotnet test` on the integration branch. B-02 only implements stages 0–3 and 11 so it will not surface there; it will surface in B-11, far from its cause.

**Fix** — add one line to the existing `PropertyGroup`:

```xml
<PropertyGroup>
  <RootNamespace>Aurora.TestKit</RootNamespace>
  <IsTestProject>false</IsTestProject>
</PropertyGroup>
```

I applied exactly this in the scratch worktree: build stays at 0 warnings and `dotnet test Aurora.sln -c Release` goes to **exit 0** with no aborted run. Do not solve it by removing the `xunit` reference — B-10 needs it for collection fixtures. While you are in the file, correct the line-11 comment to say *why* it is not targeted (because `IsTestProject` is false), so the claim and the mechanism sit together.

### Minor (candidate follow-up tasks, not blocking)

**m-1 — Pinned versions not written back into `dependencies.md`**
`Directory.Packages.props:81` and `:94`
`dependencies.md` §3 records `xunit.runner.visualstudio` as *"matching the framework major"* and `Microsoft.CodeAnalysis.PublicApiAnalyzers` as *"latest stable"*. B-01 resolved both to concrete pins (`3.1.4`, `5.6.0`) and justified them in comments, which is the right call. But `dependencies.md` §6 step 5 requires the exact version and a verification date in that file. The developer could not fix this themselves — `docs/architecture/` is architect-owned under `CLAUDE.md`. **Fix:** architect updates those two rows to `3.1.4` and `5.6.0` with a 2026-09-11 verification date. Orchestrator should route this.

**m-2 — No `.gitattributes` backing `end_of_line = lf`**
`.editorconfig:17`
The `.editorconfig` mandates LF, but nothing enforces it at the git layer. Harmless on this Linux-only toolchain; it becomes a churn source the moment anything touches the repo from Windows, and `dotnet format` will then fight the working tree. **Fix:** add a `.gitattributes` with `* text=auto eol=lf` and `*.sh text eol=lf`.

**m-3 — Dead configuration in `nuget.config`**
`nuget.config:29-32`
The `<packageRestore>` block (`enabled`/`automatic`) is a legacy MSBuild-integrated-restore setting and a no-op for SDK-style projects. It is not wrong, just inert, and this file is going to be read as the canonical example. **Fix:** delete the block.

## Finding against the spec (architect-owned; does not gate this branch)

**S-1 (major, for the architect) — verify.sh stage 4 as specified will fail on ~57 transitive packages.**
`docs/architecture/dependencies.md` §1 rule 2 says stage 4 *"lists all packages **including transitive** and fails if any is absent from this file"*. B-01's lock graph already contains 66 packages, of which **57 are transitive and absent from `dependencies.md`** — `AngleSharp*`, `BouncyCastle.Cryptography`, `Docker.DotNet.Enhanced.*`, `SSH.NET`, `SharpZipLib`, `DiffEngine`, `EmptyFiles`, `System.Management`, the `Microsoft.Extensions.*` and `xunit.*` fan-out, and others. They arrive legitimately, via approved direct packages (Testcontainers, bUnit, Shouldly, the test SDK), and all appear permissively licensed — but they are not *listed*, which is what the rule tests.

This is not B-01's doing and B-01 cannot fix it (the file is architect-owned). It is a design gap in the gate that must be resolved before B-11, or stage 4 will be red on day one and someone will be tempted to weaken it. **Fix, architect's choice:** either add a "transitive closure — licence-verified, not directly referenced" appendix to `dependencies.md` that `check-dependencies.sh` treats as an allowlist, or narrow the rule so the *name* check applies to direct references while the *licence* check applies to the full closure. Record whichever, with the reasoning, in `dependencies.md` §1.
