## What is right, so the findings below are read in proportion

The hard parts are done well and I checked them rather than took them on trust.

- `TaxRate.ApplyTo` is correct. It decomposes both operands with `decimal.GetBits`, multiplies in
  `BigInteger`, rounds once at the currency's minor unit under an explicit midpoint, and asserts its
  own postcondition. I read every branch of `RescaleWithRounding` against all five midpoint rules
  including negative amounts, and ran an adversarial 328-case boundary probe against it: **zero
  disagreements with the exact answer** (see M1 for the same probe against the naive implementation).
- Zero-value discipline holds across the contract, not just where the brief asked. `IdentifierStatus
  .Unverified = 0`, `PackageTrustLevel.Unsigned = 0` (the *least* privileged claim, and the manifest
  makes `trust` a required field so the default cannot arrive by omission), and every other enum —
  `TaxCategory`, `TaxBasis`, `ErasureHandling`, `RecordCategory`, `AccountKind`, `IdentifierKind`,
  `BalanceSide`, `TaxAmountComponent`, `ValidationSeverity`, `CountryPackageCapability` — starts at 1,
  with `Enum.IsDefined` refusing `default` at every construction site. One exception, m4 below.
- Every regex in the contract is anchored `^…\z` (`PackageId`, `PackageKey`, `PackageVersion`,
  `TaxCode`, `AccountCode`, and both ISO code shapes). `^` without `RegexOptions.Multiline` is
  equivalent to `\A`, so the anchoring is complete. `PackageKey` additionally derives `SchemaName`
  rather than reading the manifest's `schema` field, and refuses the manifest whose `schema` disagrees
  — the DDL-side value can never be anything but `pkg_` plus a lowercase word.
- The extension points are shaped so core never needs a jurisdiction branch. `AccountCode` is text
  (the note about integer parsing surviving until somebody's live ledger is exactly right);
  `RequiredForPosting` is five roles, not ten, so a tenant holding no stock is not refused over
  `InventoryAsset`; `ReportBoxSource` is genuinely closed by `private protected`; the generic
  `IEInvoicingProfile<TDocument>` is the correct way to exist before `Aurora.Documents.Canonical` does.
- `EffectiveDatingTests` proves its own scan can find a violation (`ConvenienceOverloadFixture`) and
  asserts it saw more than ten interfaces. `ContractPublicApiTests` reports the counts it compared.
  Both are the shape CLAUDE.md's self-check item 2 asks for.

### On the three judgement calls the brief raised

**`MidpointRounding` instead of `RoundingPolicy` on `TaxRuleVersion` — agreed, and it is the better
reading of the ADRs.** ADR-0021 §3 grants a package "the rounding **mode** and the rounding **basis**",
not the scale; `TaxRuleVersion` carries `Midpoint` and `Basis` and nothing else, which is that sentence
exactly. A `RoundingPolicy` would have carried a decimal-places field that `ApplyTo` structurally
cannot honour — a field that reads like a decision and is not one, which is the same defect class as a
comment claiming behaviour nothing produces. The four-line approved-API diff is the gate working.

**The embedded-vs-sidecar manifest ambiguity — routed, not resolved.** ADR-0008 §3.2 embeds the
manifest as an assembly resource; §9.3 describes a `package.manifest.json` sitting in the package
directory next to the assembly. The author implemented the embedded form and wrote no sidecar, which
is what acceptance criterion 2 asks for. Architect: §9.3 needs to say whether the signed manifest
bytes are the embedded resource (they are, in this implementation) or a separate file.

## Findings

No blockers. Four majors.

### M1 (major) — the tax property test cannot reach the region where the law breaks, by construction, and the pinned example is the only guard

`tests/unit/Aurora.Countries.Contracts.UnitTests/TaxRatePropertyTests.cs:169-182` (the generators) and
`:42-52` (the remark).

The author's honesty here is real and I want it kept: they ran the mutation, found the properties did
not fail, pinned the discriminating case, and rewrote the test's own documentation to admit the limit
instead of claiming coverage. That is the right instinct. It stops one step short of the rule, though,
and the rule is ADR-0021's Consequences: *"A property test guards it only if its generator actually
reaches the region where the law breaks."*

**The remark is too generous to the generator.** It says randomly drawn amounts "almost never land
where `decimal`'s twenty-eight digits run out". They never do — not rarely, never. `Amounts` draws a
mantissa of at most 18 digits at a scale of at most 20; `Rates` draws at most 9 significant digits at
scale 6. So the naive product needs at most 27 significant digits at a scale of at most
20 + 6 + 2 = 28, which is always exactly representable. The generator's reachable set excludes the
failure region **arithmetically**, not statistically. That is worth stating precisely, because
"almost never" invites someone to widen the ranges a little and believe the hole is closed; it is not
reachable by widening the ranges, only by changing how the amount is drawn.

**I reproduced both halves.** With `ApplyTo`'s integer path replaced by
`decimal.Round(amount * (percent / 100m), currency.MinorUnits, midpoint)`: **134 of 136 tests pass**.
The two failures are `A_product_too_precise_for_decimal_does_not_round_a_cent_into_existence` and,
incidentally, `The_rounding_policy_decides_the_midpoint_and_core_has_no_default` (only because
`decimal.Round` throws a different exception type for an undefined mode). The author's finding stands:
one example test stands between the ledger and a phantom cent.

**And the region is reachable — cheaply, deterministically, with an arbitrary generator.** Draw the
rate, the currency and a target whole number of minor units `q` arbitrarily, then *construct* the
amount that puts the exact tax one ulp below the half-minor-unit boundary:

```
amount = trunc( (2q+1) · 10^rateScale · 100 · 10^28 / (2 · 10^minorUnits · rateUnits) ) / 10^28
```

Discard the draw when the mantissa does not fit a `decimal`. I ran 500 draws: **328 constructible,
and under the naive implementation 89 of them (27%) returned a cent that does not exist** — first one
`0.4991869669468174039982830529 NZD @ 656.066808%` returning 3.28 where the exact answer is 3.27.
Against the shipped implementation, the same 328 cases produce **0 disagreements**. Runtime: 66 ms.

**Required.** Add that constructed-boundary dimension to `TaxRatePropertyTests` — arbitrary in rate,
currency, midpoint and target quotient, derived in the amount — so the property can fail on its own.
Keep the pinned example: it documents the mechanism in one readable line and pins the premise
(`writtenTheObviousWay.ShouldBe(0.0050…)`), which is a nice touch. Then correct the remark: say the
random dimension cannot reach the region and the constructed dimension is what does, and record the
89/328 figure from breaking it. One pinned example guarding a whole class of precision bug on the
money path is not enough at Full tier; a generator that can reach the region is, and it exists.

### M2 (major) — `coreContractRange` may be unbounded, so extension point 10 can be declared in a way that admits every future MAJOR core

`src/Aurora.Countries.Hosting/CoreContractGate.cs:69-80`, and
`tests/unit/Aurora.Countries.Hosting.UnitTests/CoreContractGateTests.cs:27`.

`VersionRange.TryParse` accepts `"1.0.0"` as *minimum inclusive, no maximum*. I verified against the
branch's own NuGet.Versioning: `"1.0.0"`, `"[1.0.0, )"` and `"(, )"` all report `HasUpperBound=False`
and all `Satisfies("99.0.0")`. The gate passes them. Line 27 of the gate's tests pins `("1.0.0",
"1.4.0")` as a **passing** case, so the open range is not an oversight in the parser — it is currently
approved behaviour.

That defeats the point of the field. ADR-0008 §3.1 defines a MAJOR core-contract bump as *removing or
changing the signature of a contract member*; a package cannot be compatible with a major version that
did not exist when it was built, and §5.2's fleet compatibility report is only as good as the ranges
it reads. A package declaring `"1.0.0"` today would install, silently, against core contract 2.0.0
with members removed under it — Odoo's failure class #1 arriving through the front door, past the gate
built to stop it. The gate's own message already tells authors to "use a bounded range such as
`[1.0.0, 2.0.0)`" — but only on the path where parsing failed, so the advice is never given to the
package that needs it.

**Fix.** In `CoreContractGate.Check`, after a successful parse, refuse a range that lacks either
bound: `if (!range.HasUpperBound || !range.HasLowerBound) return HostingErrors.IncompatibleCoreContract(...)`,
naming the package and the bounded form it should declare. Change the `("1.0.0", "1.4.0")` row into a
refusal case and add `"[1.0.0, )"` and `"(, )"` beside it. Consider also rejecting it at
`PackageMetadataReader` so an open range never reaches the catalogue; the gate is the minimum, because
the §5.2 fleet report goes through it.

### M3 (major) — two package-supplied structures can be cyclic, and install-time validation is the only gate before core walks them

`src/Aurora.Countries.Contracts/Reporting/IStatutoryReportDefinition.cs:153-168` and
`src/Aurora.Countries.Contracts/Accounting/AccountRoles.cs:80-96`.

`StatutoryReportVersion.Create` checks that every code a `SumOfBoxes` references is **defined in this
version** — including the referencing box itself. A box whose `SumOfBoxes` names its own code is
accepted, as is box A summing B while B sums A. `AccountRoles.Validate` has the same shape: it rejects
`account.Parent == account.Code` but accepts A→B→A.

Both validators exist precisely so a bad template fails at install with a named field instead of "at
the first tax posting, in a tenant, in production" (the comment on `AccountRoles.Validate` says so).
A definition whose evaluation does not terminate is the strongest form of that. There is no evaluator
yet, which is why this is a major and not a blocker — and it is also why it must be fixed now: B-13
and whoever writes the reporting engine will reasonably assume a definition that validated is one they
can walk.

**Fix.** Depth-first walk with a visited set in both places, reporting the cycle it found
(`"Box 'A' sums 'B', which sums 'A'"`). Two tests each: self-reference and a two-node cycle.

### M4 (major) — the contract's front-door README and its `.csproj` claim an enforcement the code does not perform

`src/Aurora.Countries.Contracts/README.md:4-7` and
`src/Aurora.Countries.Contracts/Aurora.Countries.Contracts.csproj:7-8`, against
`src/Aurora.Countries.Hosting/PackageAssemblyReferenceRule.cs:39-45`.

> "**This is the only core assembly a Country Package may reference** (ADR-0008 §3.1) —
> `Aurora.Countries.Hosting` refuses to load a package that references any other `Aurora.*` assembly"

It does not. `AllowedAuroraAssemblies` is `{ Aurora.Countries.Contracts, Aurora.SharedKernel,
Aurora.Documents.Canonical }`, and `src/Aurora.Countries.Hosting/README.md:31-33` says so correctly.
A reader has two of this branch's own documents in front of them saying different things about the
package trust boundary, and the one that is wrong is the one in the assembly a package author starts
from. The enforcement half of the sentence is new in this branch (`dd1f4f8`), and it is CLAUDE.md
self-check item 1 verbatim: *if you cannot point at the mechanism, delete the claim.*

The **code is right** — a package cannot implement `ITaxRuleProvider` without naming `Money` and
`DateRange`, so `Aurora.SharedKernel` has to be on the list, and the reasoning written on
`PackageAssemblyReferenceRule` is sound. It is the ADR sentence and these two comments that are wrong.

**Fix.** Restate both to match `PackageAssemblyReferenceRule` and point at it: the contract plus the
two tier-0 assemblies it is expressed in, enforced from package metadata before any code runs. Same
edit removes the stale `CountryContractPublicApiTests` in the `.csproj` comment — the class is
`ContractPublicApiTests`. Then route the ADR wording (below); do not edit the ADR.

## Minor findings (follow-ups, not merge blockers)

- **m1** `src/Aurora.Countries.Contracts/Localization/ILocalePack.cs:22` — "that is `RoundingPolicy`,
  and it arrives with a tax rule, not with a locale". After `914d7fd` a tax rule carries
  `MidpointRounding`; `RoundingPolicy` is referenced nowhere else in this assembly. Same shape as M4,
  smaller blast radius. Point the sentence at `TaxRuleVersion.Midpoint`.
- **m2** The manifest-agreement check (`CountryPackageLoader.cs:137-145`, ADR-0008 §3.2's *"a contract
  test enforces it"*) has no test that fails without it. The only fixture parses its own embedded
  manifest, so code and resource can never disagree. Extract the comparison into a named unit and test
  it, or add a second fixture whose `Manifest` is hand-built and wrong in one field.
- **m3** The trailing-newline case that motivated `\z` is pinned only for `PackageId`
  (`PackageIdentityTests.cs:32`). Add `"nz\n"` to `PackageKey` (it becomes a DDL schema name),
  `"1.4.0\n"` to `PackageVersion`, and the equivalent to `TaxCode`, `AccountCode` and the ISO code
  shapes. The anchors are already right; this is the regression guard that keeps them right.
- **m4** `MidpointRounding` is the one enum in this contract whose zero value is a silently valid
  choice — `default(MidpointRounding)` is `ToEven`, the *opposite* of ADR-0021 §3's core default of
  `AwayFromZero`. Inside `TaxRuleVersion` the value is always supplied, so nothing is wrong today; the
  risk is B-13 persisting the midpoint as an integer, where a missing or zero column reads back as a
  rounding rule nobody chose. Say in the contract that it is persisted by name, before rules are
  stored.
- **m5** `IStatutoryReportDefinition.VersionAsOf(DateOnly)` is not keyed by `(company,
  taxRegistration)`. ADR-0008 §8.3 and ADR-0023 §1 both say *every* statutory report slot is keyed by
  `(company, taxRegistration, asOfDate)` **in its contract signature**, so the multi-registration case
  is behaviour and UI later rather than a contract change reaching the fleet. `StatutoryReportResult`
  carries both, the definition does not. Adding them now is free; leaving them out risks a MAJOR bump
  the day a registration scheme changes which version of a return is filed. Architect decides (below).
- **m6** Nothing yet verifies ADR-0008 §10's `All_declared_capabilities_resolve`; the docs on
  `CountryPackageCapability` and `CountryPackageManifest.Capabilities` attribute it to "the installer",
  which is B-13 and honest. The nine non-generic capabilities could be checked at load for a few lines
  (`GetExtension(CountryPackageCapabilities.ContractTypeFor(capability))`), which would make a
  manifest that lies about what it contributes fail before a tenant sees it.
- **m7** `ExtensionPointRegistryTests.No_extension_point_takes_a_country_code_as_an_argument` has no
  fixture proving the scan can find a violating parameter, where `EffectiveDatingTests` does. Add one
  interface written to break it.
- **m8** `ICountryPackage` says nothing about instance lifetime or thread-safety, though one instance
  per (package, version) will serve every tenant in the process. Package-held state would be a
  cross-tenant leak through a seam none of the isolation tests look at. State the rule on the
  interface now, and make it B-13's when it starts caching `LoadedCountryPackage`.
