## Majors

### M-1 — `Aurora.Architecture.Tests.csproj` describes a fixture directory that does not exist, and carries two dead MSBuild items for it

`tests/Aurora.Architecture.Tests/Aurora.Architecture.Tests.csproj` (the `ItemGroup` added at the end
of the diff):

```xml
<!--
  Fixtures/ViolatingProjects holds .csproj files that deliberately declare forbidden project
  references. They are input data for the project-graph rules, parsed as XML. They are not in
  Aurora.sln and nothing references them, so they are never built; this Remove/None pair keeps
  them out of this project's own compilation and makes them visible in an IDE.
-->
<Compile Remove="Fixtures\ViolatingProjects\**" />
<None Include="Fixtures\ViolatingProjects\**" />
```

`Fixtures/ViolatingProjects` does not exist on this branch (`find` returns nothing; the only
occurrence of the string in the whole tree is this comment). The project-graph fixtures are written
to a temp directory by `Fixtures/FixtureProjectTree.cs`, and the project README §3 explains at length
why they must **not** be checked in — so the comment does not merely describe something absent, it
describes the design the author deliberately rejected. The `Remove`/`None` pair globs nothing.

This is `CLAUDE.md` self-check #1, in the same file type that got B-01 rejected: *"Does any comment,
name or doc claim behaviour that nothing actually produces? … if you cannot point at the mechanism,
delete the claim."* It is sharper here because the same `.csproj` comment block contains a second
claim (EF Core and ASP.NET references exist for the fixtures) that the author *did* mechanise, in
`FixtureFidelityTests`, whose own doc says it exists "so this comment is checked rather than
trusted". One half of the comment is checked; the other half is false.

**Fix:** delete the comment and both MSBuild items. While there, remove
`SolutionLayout.FixtureMarker` and the `/Fixtures/` filter in `ReadProjectsUnder` (see n-6) — they
are the other residue of the same abandoned design — or keep the filter and say in one line that it
guards against a fixture `.csproj` ever being checked in.

### M-2 — `RuleInventoryTests.Each_inert_rule_still_fires_against_its_fixture` asserts nothing of the kind

`tests/Aurora.Architecture.Tests/RuleInventoryTests.cs:179-194`. The body iterates the three inert
rows and asserts four strings are non-empty, then asserts `Inert.Length == 3`. No rule is executed,
no fixture is touched. Delete `T1_fires_on_a_public_constructor_and_on_a_protected_one`,
`T2_fires_on_AddDbContext_and_on_AddDbContextFactory` and the four `M1_fires_*` tests and this test
stays green — which is exactly the state its name denies.

The name is the problem, not the accounting: it is a universal-sounding coverage claim
("*each* inert rule *still fires*") sitting in the one class whose stated purpose is that the
difference between inert and vacuous is "written down and **checked**, not asserted". A future
reader pruning tests will trust it.

**Fix, preferred:** make the name true — it is ~8 lines. Give `Inert` a fourth column
`Func<RuleOutcome> FireAgainstFixture`:

- T1 → `TenantDbContextConstructorRule.Check(TypeIndex.Of(FixtureAssembly.AllViolations))`
- T2 → `TenantDbContextRegistrationRule.Check(TypeIndex.Of(FixtureAssembly.AllViolations))`
- M1 → `ModuleDependencyRule.Check(tree.All)` over a `FixtureProjectTree` with the Tax → Ledger edge

and assert `outcome.Violations.ShouldNotBeEmpty()` plus `SubjectsExamined > 0` for each. Keep the
string assertions.
**Fix, minimum:** rename to `Each_inert_rule_names_its_subject_and_the_task_that_brings_it` and move
the "every inert rule has a fixture test in `TenancyRuleTests` or `LayeringRuleTests`" sentence out
of the comment, since nothing produces it.

## Minors (candidates for a follow-up task, not merge blockers)

- **n-1 — the "no rule without an inventory row" gate has a hole.** `RuleInventoryTests:80-87`
  collects rule ids by reflecting for a field named `Id` that is `IsLiteral` and `System.String`.
  A rule class declaring `public static readonly string Id`, or no `Id` at all, is invisible to the
  gate, so README §2's "a rule cannot be added without someone stating what it measures" is stronger
  than the mechanism. *Fix:* also assert that every type in the `Rules` namespace whose name ends
  `Rule`/`Rules` (the convention all eleven follow) declares a literal `Id`.
- **n-2 — dangling reference in a doc comment.** `Fixtures/FixtureAssembly.cs:24` cites
  `FixtureIsolationTests`; no such class exists. The assertions it describes live in
  `ProductionPopulationTests`. *Fix:* rename the citation.
- **n-3 — the per-rule subject counts are computed and thrown away on a green run.**
  `RuleInventoryTests:99-118` builds a `report` table (`F1  21 types (floor 10) - …`) and then only
  passes it as the message of `report.Count.ShouldBe(Live.Length, …)`, an assertion that cannot fail.
  The floors *are* enforced per rule, so the check is sound; but `CLAUDE.md` #2 asks for the number to
  be **visible**, and today nobody ever sees it. *Fix:* inject `ITestOutputHelper` and write the
  table, or drop the list.
- **n-4 — `Aurora.Documents.Canonical` is tier 0 and no rule constrains its `PackageReference`s.**
  The L1 narrowing is otherwise correct and the author's justification is verified: ADR-0008 §3.1
  does require `Microsoft.CodeAnalysis.PublicApiAnalyzers` on `Aurora.Countries.Contracts`, so
  sweeping it into L1's declared half would indeed ban a dependency the architecture asks for
  (this is the B-12 claim, and it holds). `Aurora.Documents.Canonical` has no equivalent need, and
  `ProjectLayeringRule` only reads `ProjectReference`, so a `Newtonsoft.Json` package reference on a
  shared kernel that Sales, Purchasing, DocumentExchange and every Country Package depend on would
  pass every rule here. *Fix:* add `Aurora.Documents.Canonical` to
  `DomainPurityRule.CheckDeclarations`'s scope only (not the compiled half, whose kernel-only
  reference rule would be wrong for it), or record in README §1 why it is left out.
- **n-5 — "every test class here carries `[Trait("Category", "Architecture")]`" is true and
  unenforced.** All nine classes carry it today; nothing fails when the tenth does not, and B-11's
  stage 7 will select on that trait. *Fix:* one test asserting every class in this assembly holding a
  `[Fact]`/`[Theory]` declares the trait.
- **n-6 — `SolutionLayout.FixtureMarker` and the `/Fixtures/` project-discovery filter are dead**
  (no `.csproj` lives under a `Fixtures/` folder). See M-1.
- **n-7 — T5's subject count does not include its second population.**
  `TenantScopeRules.cs:122-127` reports `SubjectKind = "types, plus the types named by singleton
  registrations"` but `SubjectsExamined = index.All.Length`. The count names one population and
  measures another. *Fix:* add `singletons.Count`, or shorten the kind to "types".
- **n-8 — two ADR-0027 rules are deferred with no backlog id.** README §6 records, with good
  reasons, that §1's "every tenant `DbContext` constructor takes exactly one `TenantAccess`-derived
  parameter" and §2's `AllowUnstampedDuringProvisioning` call-site restriction are not here. That is
  the right call — both would have to guess a type that does not exist — but a deferral recorded only
  in a test project's README is a TODO without a backlog ID. **Route to the project-manager:** add
  them to the B-06.3 and B-07.1 rows.
- **n-9 — `ProjectLayeringRule` is slightly wider than `solution-layout.md` §2 for
  `.Infrastructure`.** §2's table allows `<M>.Application` and Npgsql; the rule also allows tier 0
  and `Aurora.Platform.*.Contracts`. That matches `modules.md` §6 (Kernel ✅, Platform ✅ on every
  consumer row) and is almost certainly right, but the rule's comment cites §2 alone. *Fix:* cite
  `modules.md` §6 for that row too.

## Route to the architect

**The ADR-0020 deviation is recorded only inside the test project.** `README.md` §5 and the `.csproj`
comment state it clearly and argue it well, but `docs/decisions/ADR-0020-test-tooling.md` still names
`TngTech.ArchUnitNET` as the architecture-test mechanism, `docs/architecture/testing-strategy.md` §5
still says the project reflects over assemblies "(ArchUnitNET)", `docs/architecture/dependencies.md`
line 116 still lists both ArchUnitNET packages as "Architecture fitness tests", and
`Directory.Packages.props` still pins `TngTech.ArchUnitNET` 0.13.4 and `.xUnit` 0.13.4 with **no
consumer anywhere in the solution**. The author could not fix any of the first three — they are
architect-owned — and did the right thing by asking. But the current state is a repository that
contradicts itself on its only memory, and the next developer writing a fitness rule will read
ADR-0020, add ArchUnitNET, and the solution will carry two mechanisms for one job.

**The deviation itself is justified.** ADR-0020's own words are "source-level rules are Roslyn
analyzers/tests, because reflection cannot see them"; `docs/reviews/B-03.md` m-1 is the proof
(verified — the finding exists as cited), and `solution-layout.md` §6 row B-04 then *requires* F1 to
catch a `double` local and a `(double)` cast. I confirmed below that IL scanning catches exactly
that. `System.Reflection.Metadata` is in-box, so no new dependency and no licence question, and the
scanner is ~720 lines behind one interface, which is the same containment ADR-0020 already accepts for
ArchUnitNET's pre-1.0 risk. My recommendation to the architect: **amend ADR-0020** to say IL
metadata scanning is the mechanism for assembly-level rules, decide whether ArchUnitNET stays an
approved option or is removed from `dependencies.md` and `Directory.Packages.props`, and correct
`testing-strategy.md` §5's opening sentence.

## What I verified, and how

### 1. Can each rule actually fail? — planted in real `src/` code, built, watched red, reverted

The author's table was not taken as evidence. I planted **eleven real violations in production
projects**, rebuilt the solution in Release and ran the suite. Every rule in the inventory fired, on
compiler output, naming the planted subject. Each experiment was reverted (`git checkout -- .`) and
the suite re-run green (109/109) before the next.

The three **inertness guards** were planted against too, and all three expired loudly as advertised:
`No_tenant_DbContext_exists_yet_…`, `No_tenant_access_type_exists_yet_…`,
`No_tenant_DbContext_factory_exists_yet_…` and `Fewer_than_two_business_modules_exist_…` each went
red the moment the awaited type or the second module project appeared. This answers the brief's
specific worry: the simple-name matching is not a rule that cannot fire — a type merely *named*
`TenantScope` or `TenantDatabaseHandle` in production trips both the rule and the guard.

Both **population guards** were also proven, not assumed:

- removing one built assembly (`Aurora.Documents.Canonical.dll`) turned **19 of 109** tests red with
  "these projects under `src/` produced no assembly, so the architecture rules would have run over an
  incomplete population";
- planting a source file without rebuilding produced "source files newer than their compiled
  assembly … the rules would have inspected the previous build". The `SolutionLayout` staleness
  refusal is real and is the single most valuable thing in this branch after F1 itself.

### 2. Does every rule report what it examined?

Yes. `RuleOutcome` carries `SubjectsExamined` + `SubjectKind` and every rule populates it;
`RuleAssert.Holds` takes a mandatory floor; `RuleInventoryTests` re-runs all eight live rules with a
per-rule floor (10 for the type-population rules, 3 and 1 for the project-graph ones). The counts are
non-zero for every live rule on a clean tree — the suite passes those floors, and I saw the real
numbers in the failure output (F1 21 types with one planted type, S3 19, T3/T5/T6 32 with plants,
L1-L5 7 declared references with plants). Two caveats are recorded above as n-3 (the counts are never
*displayed* on a green run) and n-7 (T5's count names a population it does not measure). Neither
makes a rule vacuous.

The three inert rules are the only ones with floor 0, each is named in `Inert` with the task that
brings its subject, and each has an inertness guard I proved fires. That is the correct shape.

### 3. Names, comments and README claims versus mechanisms

This is where the two majors are (M-1, M-2), plus n-1, n-2 and n-5. Everything else I spot-checked
held:

- F1's "What it cannot see" paragraph is accurate (`object`-boxed floats, arithmetic in an
  unscanned assembly) and the population is every project under `src/`, so the second case is closed
  by construction.
- T5's name says "field or property", not "holds", and the doc states the two things it cannot see
  (non-generic `ServiceDescriptor`, captured closures). Accurate.
- The README's `L1` scope claim matches `testing-strategy.md` §5.1 word for word, and the B-12
  analyzer justification is verified against ADR-0008 §3.1.
- `ModuleMatrix` is a faithful transcription of `modules.md` §6: I checked all eleven rows,
  including the three the doc calls out (Ledger → Parties E, Payments ✗ Products, the Sales /
  Purchasing / Payments peer E cells). Unknown consumer = refused, which is the safe default.
- `ProjectIdentityTests` pins all sixteen naming cases and asserts no project in the solution
  classifies as `Unknown` — the guard that stops the convention drifting into a solution nothing
  constrains.

### 4. Deleting `SharedKernelAssemblyTests` — no coverage lost

Verified by reading the deleted file against the new rules. Old F1-kernel reflected over fields,
properties, parameters and return types of one assembly; new F1 does all of that plus locals, IL
opcodes and called-member signatures, over every production assembly — a strict superset (and the
old one is the rule B-03's review found defective). Old L1-kernel read
`GetReferencedAssemblies()`; new L1 does that plus declared `PackageReference`/`FrameworkReference`,
the committed lock file's `Direct` entries, a missing-lock-file violation, and banned namespaces that
live in BCL assemblies (`System.Text.Json`) — also a strict superset. The one property genuinely
lost is "a kernel change fails in the kernel's *own* test run"; the staleness guard plus stage 6
running both projects covers it, and I confirmed the staleness guard fires. The `.csproj` and README
in `src/Aurora.SharedKernel` were updated to point at the new mechanism and now describe it
accurately.

### 5. Acceptance criteria (`solution-layout.md` §6 row B-04, ADR-0007 §12.3, ADR-0027 §1)

All met. Domain purity (L1), module matrix (M1), no `double`/`float` — solution-wide and
body-deep (F1), no ambient clock in domain/application (S3), `IHttpContextAccessor` confined (T4),
no `AddDbContext` of a tenant context (T2), no public constructor on a tenant context (T1), no
`ITenantDbContextFactory<>` outside `Aurora.Platform.Tenancy` (T3, extended to ADR-0027's
`ITenantMigrationContextFactory<>`), no `TenantScope` on a singleton (T5, extended to
`TenantDatabaseHandle` and `TenantAccess`). ADR-0027 §1's `TenantDatabaseHandle` allow-list (T6)
landed in this slice rather than as a fast-follow, which answers the open question in the B-04
backlog Notes. Every rule has a deliberately-violating fixture *and* — now independently confirmed —
fires on a real violation in `src/`.

- **Ownership:** the diff touches `src/`, `tests/` and `scripts/` only. No `docs/decisions/`,

- **Dependencies:** `Microsoft.EntityFrameworkCore` (10.0.12) and the `Microsoft.AspNetCore.App`

## Note for future reviews of this codebase

A new instance of the recurring pattern, worth carrying forward: **when a design is abandoned
mid-task, its justification often survives in a comment.** M-1 is a `.csproj` comment describing
checked-in fixture projects that the author consciously replaced with temp-directory fixtures — the
README even argues against the approach the comment describes. When reviewing, grep every path,
directory and class name that a comment mentions and confirm it exists; both majors here were found
that way, and B-01's rejection was the same shape.
