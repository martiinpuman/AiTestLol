### Major

**M-1 — Stage 6 prints `PASS` when zero tests execute, and nothing in the backlog will ever make it notice**
`scripts/verify.sh:434-455` (`stage_unit_tests`), summary rendering at `:645-648`

The stage runs `dotnet test --filter 'Category!=Integration&Category!=Ui'` and treats a zero exit as a pass. On today's skeleton that means the gate's central stage is green while measuring nothing. I confirmed the shape directly:

```
$ ./scripts/verify.sh --filter 'FullyQualifiedName~ZzzDoesNotExist'
 6   Unit tests                  PASS  1.8s
 RESULT: PASS
```

and in `artifacts/verify/06-unit-tests.log`:

```
No test matches the given testcase filter `(Category!=Integration&Category!=Ui)&(FullyQualifiedName~ZzzDoesNotExist)` in .../Aurora.Architecture.Tests.dll
No test matches the given testcase filter ... in .../Aurora.Web.ComponentTests.dll
```

`PASS` here is indistinguishable from "every test in the solution was silently excluded". A misspelled `[Trait("Category", ...)]` value, a filter typo, a test project dropped from `Aurora.sln`, or a discovery failure all produce exactly this output.

The author disclosed this honestly, and I accept that a hard floor cannot be imposed today — the solution genuinely has no tests and B-03 is in flight, so failing on zero would make the integration branch red, which `CLAUDE.md` forbids. That is not what makes this major. What makes it major is that **the gate has no mechanism to ever notice, and no task owns adding one.** §6/backlog row B-11 covers stages 4, 5 and 7–10; its only stage-6 clause is "unit stage passes with Docker stopped". Once this merges, stage 6 is finished work and nobody returns to it. This is the same shape as B-01's M-1 — a command that succeeds when it should shout — and the project's own `testing-strategy.md` §1 rule 4 is the standard being missed: *"A green rule that cannot fail is worse than no rule, because it is trusted."* Stage 6 can fail (cases 11 and 12 prove it); what it cannot do is tell that it measured nothing.

**Fix** — the `.trx` files stage 6 already writes to `--results-directory` carry the counts. In `stage_unit_tests`, after a successful `run_cmd`:

1. Sum the `Counters` `total`/`executed` attributes across `"${VERIFY_DIR}"/*.trx` (a `grep -o 'total="[0-9]*"'` is enough; no new tool).
2. Always set `STAGE_NOTE[6]` to `"N test(s) executed"`, so the summary row reads `6 Unit tests PASS 1.8s 0 test(s) executed` and `PASS` can never again be confused with nothing-ran. The `Note` column already exists and is unused for passing stages.
3. Fail the stage when the count is below a named constant declared next to `FAIL_TAIL_LINES`:

```bash
# Zero today: the solution has no tests yet (B-03 lands the first ones).
# Raise this in the same commit that adds them — a stage that measures
# nothing must not be able to report PASS silently.
MIN_UNIT_TESTS="${AURORA_MIN_UNIT_TESTS:-0}"
```

with the failure message naming the filter that was applied. That is non-breaking today, gives the property a visible home, and turns "raise the floor" into a one-line change that the next developer can see. Add a self-test case with `--filter` matching nothing plus `AURORA_MIN_UNIT_TESTS=1`, asserting `RESULT: FAIL - stage 6` — that case is the proof the mechanism works, and it will keep working after the floor is raised.

### Minor (candidate follow-ups, not blocking)

**m-1 — Stage 11's working-tree guard has no self-test case.**
`scripts/verify-selftest.sh:416-429`. The harness covers stages 0, 1, 2, 3 and 6, but not 11 — and stage 11 is the mechanism that enforces §5.1's central promise that the gate never mutates what it measures. It is also the stage most likely to be regressed by B-11, which adds stages that read and (must not) write lock files and the dependency closure. I verified by hand that the guard fires; there should be a case that does.

**m-2 — The tree guard never runs when an earlier stage fails.**
`scripts/verify.sh:665`. Fail-fast `exit 1`s out of the stage loop, so stage 11 is never reached. A mutation introduced by stage 1 or 2 on a run that then fails at stage 3 goes completely unreported — which is the case where a developer is least likely to notice it, because they are already reading a failure. **Fix:** move the comparison into `on_exit` (verify.sh:576) so it is evaluated on every exit path, and let stage 11 simply report what the handler found. Keep it advisory when the run already failed for another reason, so the primary failure stays the headline.

**m-3 — `case_offline` can now cover stage 6 and the full run.**
`scripts/verify-selftest.sh:250-272`. The comment says "the day this image gains `ip`, add it to the loop behind `ip link set lo up`". That day is today: loopback can be raised without `iproute2` via a `SIOCSIFFLAGS` ioctl from `python3`. I ran the full gate this way — exit 0, 13.1s, tree clean. **Fix:** replace the comment's deferral with the recipe and extend the case to a full offline run, so §5.1's "no network access required" becomes a tested property of the whole gate rather than of stages 0–3 only.

**m-4 — The documented options are untested.**
`scripts/verify.sh:124-180`. `--fast`, `--no-docker`, `--filter` and `--stage` are user-facing contract from §5.3, and `--filter` in particular is wired into the one stage that matters most. I verified them by hand (exit 2 on bad usage, `--stage <pending>` exits 2 naming the owning task, correct SKIP notes), but nothing in the harness will catch a regression. **Fix:** add one case asserting exit 2 for `--bogus` / `--stage 99` / `--stage 4`, and one asserting `--fast` marks 8–10 `SKIP` with the note `--fast`.

### Nits (take or leave)

**n-1 — The summary table's result column is never coloured.**
`scripts/verify.sh:568`. `result="$(awk '{print $2}' <<<"${line}")"` reads field 2, which is the first word of the *stage name*, not the result — so `result_colour` always falls through to `C_DIM`. Confirmed on a pty: the live progress line renders `^[[32mPASS`, but the summary row renders `^[[2m 0 Preflight PASS ... ^[[0m`. A FAIL row in the table is dim, not red. **Fix:** `awk '{print $3}'`, or match on the line content directly.

**n-2 — `now_ms` dereferences `EPOCHREALTIME` under `set -u`.**
`scripts/verify.sh:199`. Bash 5.0+ only; on bash 4 the gate aborts with an unbound-variable error before printing anything. Irrelevant on this Linux-only toolchain, relevant the first time someone runs it on a macOS default shell. **Fix:** fall back to `date +%s%3N`, or assert `BASH_VERSINFO[0] -ge 5` in the preamble with a message.

**n-3 — The self-test's backup directory path is never printed.**
`scripts/verify-selftest.sh:46`. The `EXIT`/`INT`/`TERM` traps cover everything except `SIGKILL` and a power cut — and after one of those the user has a deliberately-defective working tree and no pointer to where their originals went. Every staged path happens to be git-tracked except the injected probe file, so `git checkout -- .` recovers, but the script does not say so.

**n-4 — `assert_no_build_warnings` treats a missing MSBuild summary as "no warnings".**
`scripts/verify.sh:410-422`. Documented as deliberate, and correct today — case 10 proves the grep matches, and `03-build.log` contains `    0 Warning(s)`. But if the MSBuild terminal logger ever becomes the default for `dotnet build`, that line disappears and the check goes silently inert. Same silent-vacuity family as M-1, at much lower stakes because `TreatWarningsAsErrors` still covers compiler warnings. **Fix:** track whether any summary line was seen and fail if none was.

**n-5 — The change touches three files, not two.**
`scripts/dev-env.sh:4-9,21-23` gains `AURORA_SKIP_DOCKER`. The change itself is good — backward compatible (defaults to `0`), well-commented, and it is what makes `--no-docker` cost nothing on a machine with no daemon. Recording it only because the task report described the diff as two files; a shared script that every agent sources deserves to be named in the summary.

## Patterns noted for this codebase

**A gate stage must be able to distinguish "all green" from "nothing ran".** B-01's M-1 was a command that failed loudly in the wrong place; B-02's M-1 is the mirror image — a command that succeeds quietly when it measured nothing. Both went unnoticed because the reported outcome was a single word with no cardinality attached. For every stage this gate grows, ask: *what number did it measure, and is that number visible in the summary?* Packages licence-checked, advisories scanned, tests executed, rules asserted, tenants migrated — a stage that reports PASS without a count is a stage that cannot report its own vacuity. This extends the B-01 pattern ("does any comment claim behaviour that no property in the file actually produces") from build files to the gate itself.

**The corollary, which this branch gets right and should be the house standard:** every enforcement mechanism ships with an executable demonstration that it fails when it should. `scripts/verify-selftest.sh` is the concrete form of `testing-strategy.md` §1 rule 4 for shell tooling, and B-11 must extend it rather than start a second harness — the file already says so at line 20. When a reviewer verifies a claim the harness does not make (as I did for the stage 11 guard and for stage 6's offline behaviour), that verification belongs back in the harness as a case, not only in a review document.
