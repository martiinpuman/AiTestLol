## Findings

### Major

**M-1 — `ALTER DEFAULT PRIVILEGES` silently grants the request-path role `DELETE` on every future catalog table, including the append-only ones**
`src/platform/Aurora.Platform.Tenancy/Migrations/20260911172124_InitialCatalog.cs:226-228`

```sql
ALTER DEFAULT PRIVILEGES FOR ROLE aurora_migrator IN SCHEMA catalog
GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO aurora_app;
```

Probed against the migrated fixture: created `catalog.operator_audit_event` as `aurora_migrator`, then as `aurora_app` `has_table_privilege` returned **True for DELETE** and the `DELETE` executed. `catalog.operator_audit_event` is ADR-0007 §9.2's "append-only; every operator action, incl. support access" and `catalog.erasure_replay_log` is §11.5's restore-replay record; **ADR-0004 rule 5 requires `UPDATE`/`DELETE` to be revoked from `aurora_app` on append-only tables.**

This inverts the default from fail-closed to fail-open for every table B-07, B-08, Messaging, Audit and Configuration will add, and the only thing between that and a deletable audit trail is the migration's own comment — a rule to remember, in a change that elsewhere argues persuasively against rules to remember. It also permanently alters the database: removing the line later does not retroactively fix a table created in between.

**Fix** (first preferred):
1. Delete the statement. Each future catalog table grants explicitly in its own migration; forgetting produces a loud `42501` at first use rather than a silent over-grant.
2. If kept, default to `SELECT, INSERT` only — never `UPDATE, DELETE`.
3. Either way, add a privilege test enumerating `information_schema.role_table_grants` for `aurora_app` in schema `catalog` against an explicit per-table expectation map, in the spirit of `CatalogSchemaAllowlist`, so a new catalog table forces the privilege decision into a reviewable diff.

**M-2 — the "CONNECT on exactly one database" claim is false under the model that ships, and the test's name universally quantifies what it proves for one database**
`tests/integration/.../CatalogPrivilegeTests.cs:22-25,:94` · `src/platform/Aurora.Platform.Tenancy/README.md:106-108` · `tests/integration/README.md:21-26`

Both documents state: "`aurora_app` holds `CONNECT` on exactly one database (ADR-0007 §4.4), so a compromised or mis-routed request cannot reach another database on the cluster." **§4.4 says "Under §3.5 stage 2 it additionally has `CONNECT` on exactly one database"** — and §3.5 stage 1, what ships, is "one `aurora_app` login role per cluster" with `GRANT CONNECT` on every tenant database.

Confirmed in the fixture's own cluster: as `aurora_app` I connected to `template1` and to a freshly created `aurora_t_probe`. The test proves only that it cannot reach the *maintenance* database, because that is the one the fixture hardened.

This matters more than a doc slip: the module README is what B-06's and B-07's implementer will read, the passage is offered as the substitute for the DoD's tenant-isolation test, and a reader who believes the role already bounds the blast radius may deprioritise the §4.3 identity check that actually does.

**Fix:**
- Rename to `The_app_role_cannot_connect_to_the_maintenance_database`, or make the name true by enumerating `SELECT datname FROM pg_database WHERE datallowconn` and asserting the app role can open only the catalog — which would also force the fixture to harden `template1` the way a real cluster must.
- Correct both READMEs and the remarks to quote §4.4 with its qualifier: today `aurora_app` is one role per **cluster**; sideways containment rests on §8 step 3's per-database `REVOKE ALL … FROM PUBLIC` plus explicit `GRANT CONNECT`, and on §4.3's identity check.
- State what B-07 must add rather than implying the property already holds.

### Minor (follow-ups, not merge blockers)

**m-1 — the migrated-schema §9.3 guard inspects ordinary tables only.** `CatalogHoldsNoTenantBusinessDataTests.cs:29` uses `relkind = 'r'`. §9.3's escape hatch is "a catalog-owned summary table", and a materialized view or partitioned parent is a plausible shape for one. Fix: `relkind IN ('r','p','v','m','f')`, or state the limit in the remarks as the `settlement_minor_units` limit is stated.

**m-2 — `ck_database_cluster_secret_refs_are_references` does not mirror `SecretReference.IsWellFormed`, though two comments say it does.** `[=;[:space:]]` misses other control characters, and an empty string passes. Fix: `~ '^[^[:space:][:cntrl:]=;]+$'`, or narrow both comments.

**m-3 — `dotnet-ef` is a third-party tool with no `dependencies.md` entry and no gate that can see it.** `.config/dotnet-tools.json` is outside both tiers of stage 4, which reads project lock files. MIT, and its sibling is already recorded, so bookkeeping not risk. Architect-owned; note for B-11 that stage 4 should read the tool manifest as a third input.

**m-4 — `InternalsVisibleTo` is the hinge of the accessibility argument and nothing tests it.** A third grant would silently falsify "a module cannot write a query over the tenant registry at all". Fix: assert the grant list, or hand the rule to B-04.

**m-5 — `InitialCatalog` will trip B-09's `CREATE INDEX` rule as §7.2 rule 2 is written.** Six indexes without `CONCURRENTLY`, correctly, because the tables are new in the same migration — but the scan is stated unconditionally. Someone must decide whether the rule exempts same-migration tables.

**One more for the architect:** §4.4's second sentence is easy to quote without its "Under §3.5 stage 2" qualifier — M-2 is exactly that mistake, made by a careful author. Restate §4.4 as two labelled bullets so the trap is gone.

## DoD criterion 3, and what B-07 must add

**I agree with the author's reading.** A partition-style isolation test over a database shared by design would assert nothing, and §12.2's contract presupposes two tenant databases that do not exist until B-07. Testing the blast radius of the role the request path holds is the right substitute. What is wrong is the *claim attached to it* (M-2), not the choice of test.

What B-07 (with B-10) must add:
1. The six §12.2 tests over two real tenant databases provisioned by the real saga, including the deliberate mis-route asserting `TenantRoutingViolationException`. **Under §3.5 stage 1 that mis-route test is *the* cross-tenant control**, because `aurora_app` legitimately holds `CONNECT` on every tenant database.
2. §8 step 3's hardening asserted by querying the resulting privileges — `REVOKE ALL … FROM PUBLIC` proved by *attempting a connection* as an ungranted role, the same lesson this task's fixture bug taught — plus `DROP SCHEMA public` and `btree_gist`.
3. A cluster-level assertion enumerated over `pg_database` rather than demonstrated on one database, covering `template1` and the maintenance database.
4. When §3.5 stage 2 lands, the "CONNECT on exactly one database" test this task's name promises.

## Summary

Fix M-1 and M-2 — one SQL statement plus one test, and a rename plus three corrected paragraphs. The minors are good follow-ups and should not hold the merge. Given the tier and that the majors touch the privilege model of the only shared database, the rework should come back for a **second reviewer's re-review**.
