# Backlog

Owned by the project-manager. The orchestrator updates the Status column as work moves.

Statuses: `draft`, `ready`, `in-progress`, `review`, `changes-requested`, `done`, `blocked`.

**How to read "ready" here.** Every row below marked `ready` is fully specified and scoped to fit one developer session, per the project-manager role's definition of ready. The **Depends on** column is authoritative for actual dispatch order — most rows below depend on `B-01` directly or transitively, and since nothing is `done` yet at bootstrap, only `B-01` is literally unblocked right now. The rest are marked `ready` (rather than `draft`) because their specs are complete and nothing further needs grooming before a developer can pick them up **the moment their dependency reaches `done`** — this is what "keep at least 5 ready tasks ahead of the developers" (the project-manager role) means in practice: the queue never runs dry waiting on the project-manager. The orchestrator should not dispatch a `ready` task ahead of an incomplete dependency; it should treat this table as the next several waves of work, groomed in advance.

**The new Tier column** names the review depth from `CLAUDE.md`'s Review tiers table (Full / Standard / Light) for every task that ships code. It is not the module-dependency "tier" used in `architecture/modules.md` (tier 0 kernel, tier 1 platform, …) — a different axis, same word; do not confuse them. `—` marks a row that is not developer-reviewed code (a ui-designer deliverable).

Bootstrap tasks `B-01` … `B-15` are the architect's walking-skeleton sequence (`docs/architecture/solution-layout.md` §6), reproduced here with real dependency ordering and, where the task is pure platform/engineering scaffolding with no product-facing "problem and user," the architect's own acceptance criteria stand as the spec (see Spec column) rather than a duplicate product document — a PM spec exists only where the task has real business/tenancy/permission/audit shape a developer would otherwise have to guess at (`B-07`, `B-15`). `B-15` itself was split into three backlog rows (`B-15.1`/`.2`/`.3`) because, as specified, it bundled domain+application+infrastructure+API+UI+two-tenant testing into one task that did not fit a single session.
