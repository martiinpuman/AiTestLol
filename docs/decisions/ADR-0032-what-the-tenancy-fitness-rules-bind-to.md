## 1. Context

B-04's second reviewer executed four bypasses of the tenancy fitness rules (`../reviews/B-04-rereview.md`). Two are defects in rule code and belong to that task. **Two are not:** the rules are as wide as ADR-0007 made them, and ADR-0007 did not say where the boundary is.

| Attack, executed | What walked past | Why it is this ADR's problem |
|---|---|---|
| `services.AddScoped<SalesDbContext>()` | T2, which keys on the member name `AddDbContext*` | ADR-0007 §4.2 says "no tenant `DbContext` is ever registered"; it lists three EF Core APIs. A rule cannot enforce a sentence that names three APIs against a container that has thirty |
| `Register<TContext>(s) => s.AddDbContext<TContext>()`, called with the concrete type elsewhere | T2, which counted the helper's call as an *examined subject* and found its generic argument to be `!!0` | The population floor looked healthy while the violation was unreachable. **B-06 will naturally want `AddTenantDbContext<TContext>()`**, which defeats a name-keyed rule by construction |
| `public static SalesDbContext Open(...)` on a type whose context constructor is `internal` | T1 (whose doc says this is "T3's job") and T3 (which reads interface lists only) | ADR-0007 §4.1 closes the constructor door and says the factory is "the only public way". Nothing said whether a *member returning* a context is a second door |
| An assembly named `Aurora.Platform.TenancyBypass`; a type named `CatalogDbContext` in any namespace | T3 and T6 (prefix allow-lists) and T1/T2 (simple-name exemption) | The authorisation and the exemption are both things the violating code chooses for itself |

A developer is reworking B-04 now with a placeholder predicate waiting on the first two answers, and B-06 writes the registration code next. Until B-06 lands, these rules are the *only* thing that will catch a violation of `CLAUDE.md`'s guarantee — "a developer must not be able to obtain a `DbContext` without a resolved tenant".

### 1.1 What the scanner can and cannot see today

Every mechanism below is checked against the model B-04 already built (`tests/Aurora.Architecture.Tests/Metadata/ScannedModel.cs`), because a decision that needs a capability the scanner does not have is a decision that will be quietly downgraded during implementation.

**Visible today:** assembly name and full type name per type; `TypeAttributes` (so type visibility, including nested); method accessibility (`MethodAttributes`, and a property's accessors are methods, so their accessibility is visible); field accessibility (`FieldAttributes`); return types, parameter types and locals as `TypeUse`, whose `Names` set is *flattened whole names* (so `ValueTask<SalesDbContext>` names the context and `SalesDbContextModelSnapshot` does not); and per instruction, the opcode, the declaring type, the member name, the signature and the generic arguments.

**Not visible today:** custom attributes; generic-parameter constraints; string operands (`AssemblyScanner.IsTokenOperand` excludes `InlineString`, so a `Type.GetType("…")` lookup really is invisible); and — the one that changes a decision below — **the closed generic arguments of an instruction's declaring type**. `AssemblyScanner.NameOfTypeHandle` renders a `TypeSpecification` and trims it at the first `<`, so a call to a member of `TypeHelper<SalesDbContext>` records the declaring type as `TypeHelper\`1` and the context name appears in **no** operand of the calling assembly. §4.1.1a specifies the extension that closes this, because it is the difference between Decision 2 being implementable and being a sentence.

**This is why no decision below uses an attribute as its boundary** — an attribute-keyed rule would need a scanner extension first, and would then key on a mark the violating code can apply to itself anyway.

## 2. The one principle behind all four decisions

> **A rule may only key on an identity that the violating code cannot mint for itself.**

The same defect appears three times in the re-review, wearing three costumes:

- a **method-name** key (`AddDbContext*`) lets the author of a violation choose a different method name, or wrap the call in one;
- an **assembly-name prefix** (`Aurora.Platform.Tenancy`) lets a new project authorise itself by being christened `Aurora.Platform.TenancyBypass`;
- a **simple type name** (`CatalogDbContext`) lets any type opt out of T1, T2 and the inertness guard by choosing that name.

An assembly's *exact* name and a type's *full* name are also chosen by a developer — but changing them is a diff in a `.csproj` or a namespace declaration that a reviewer sees, and there is exactly one assembly per name in the solution. **That last clause is load-bearing, so it gets a mechanism rather than a hope:** `SolutionLayout.ExpectedAssemblyPath` derives the expected `.dll` from the project file name, so an `<AssemblyName>` override that duplicates another project's assembly name makes `ProductionAssemblies` throw and every rule test fail loudly. That is enforcement by accident, and accidents move — so the change that implements these rules also adds the one-line assertion that **no two production projects produce the same assembly name**. That is the difference between a boundary and a convention: **a boundary is an identity whose change is a reviewable event; a convention is a name a rule hopes nobody will take.**

Ranked by that principle, the candidate boundaries a rule reading IL could use are:

| Boundary | Can the violating code mint it? | Visible to today's scanner? | Verdict |
|---|---|---|---|
| Exact assembly name | Only by a `.csproj` change a reviewer sees | Yes | **Use it** |
| Full type name | Only by a namespace change a reviewer sees | Yes | **Use it** |
| Member accessibility + declaring-type visibility | No — it is a property of the declaration, not a name | Yes | **Use it** |
| Opcode (`newobj`) | No | Yes | **Use it** |
| Method name / name prefix | Yes, freely | Yes | Reject as a boundary |
| Assembly-name prefix | Yes, freely | Yes | Reject as a boundary |
| Simple type name | Yes, freely | Yes | Reject as a boundary |
| Custom attribute | Yes, freely | **No** | Reject twice over |
| Marker interface | Yes, freely; and it marks types, not call sites | Yes | Reject |

## 4. Decision

### 4.1 Decision 1 — **every DI registration that names a tenant `DbContext` is banned, whatever the method. There is no sanctioned registration helper.**

`AddTenantDbContext<TContext>()` must not be written. Nor `AddScoped<SalesDbContext>()`, nor a `ServiceDescriptor` built from `typeof(SalesDbContext)`, nor a generic wrapper that passes a tenant context to any of them.

The exemptions are two, both identified by exact names, not by shape:

1. **`Aurora.Platform.Tenancy.Catalog.CatalogDbContext` in assembly `Aurora.Platform.Tenancy`** is not a tenant context and is registered conventionally (ADR-0003 rule 3, ADR-0007 §4.2, §4.3 of this ADR).
2. **The open-generic factory registration** in `Aurora.Platform.Tenancy`: `services.AddScoped(typeof(ITenantDbContextFactory<>), typeof(TenantDbContextFactory<>))`, and the same shape for ADR-0027's `ITenantMigrationContextFactory<>`. This is not an exemption in the rule at all — **it names no context type**, so no rule below can match it. That is the point: the sanctioned path is invisible to these rules by construction rather than by allow-list.

#### 4.1.1 The mechanism

**T2 (amended) — the `AddDbContext` family is called from exactly one place.** Key: **the call site's assembly and the argument's full name, never the member name.**

- Population (counted): every instruction whose member name begins `AddDbContext`, `AddDbContextPool`, `AddDbContextFactory` or `AddPooledDbContextFactory`.
- Violation: **any such call in a production assembly other than `Aurora.Platform.Tenancy`** — whatever its generic argument, *including a generic argument that is a type parameter* (`!!0`, `!0`). An argument the rule cannot resolve is a violation, not a silence.
- Violation: such a call inside `Aurora.Platform.Tenancy` whose generic argument is anything other than `Aurora.Platform.Tenancy.Catalog.CatalogDbContext`.
- Consequence for the helper attack: the helper's own body (`s.AddDbContext<TContext>()`) is reported wherever it lives, because it is the site and not the argument that is judged.

**T15 (new) — no container-facing code names a tenant `DbContext`.** Key: **the container surface** — a *segment-bounded namespace prefix* for the declaring types of calls, and a short list of *exact type names* for signatures. Never a member name.

- A **call site** is container-facing if **either** (i) the called member's declaring type sits under the namespace `Microsoft.Extensions.DependencyInjection` or `Microsoft.Extensions.Hosting`, segment-bounded (`ns == prefix || ns.StartsWith(prefix + ".")`) — which puts `Microsoft.Extensions.DependencyInjection.Extensions.ServiceCollectionDescriptorExtensions.TryAddScoped` in scope and keeps a hypothetical `Microsoft.Extensions.DependencyInjectionTools` out — **or** (ii) the **called member's own signature** names one of the five container-surface types below — **in any position, parameter or return, and in any member, framework or project.** That generality is the limb, not a side effect of it: the key is the shape of the member being called, so it cannot be evaded by moving the registration behind a helper, and it does not care who wrote the member. Reason it is spelled out: the first statement of limb (ii) reasoned only about project helpers, and the framework member it also matches was therefore missed — see the floor below.
- **Limb (ii) exists because this ADR twice explained a report by it while defining only limb (i)** — a finding raised in two consecutive reviews, which by `ORCHESTRATION.md`'s rule makes the ambiguity itself the finding. It is not merely bookkeeping: without limb (ii), a call into a project-specific registration helper is container-facing only when its *enclosing* method happens to hold an `IServiceCollection`, so `internal static void Go() => Registrar.RegisterContext<SalesDbContext>(Holder.Services);` — no `IServiceCollection` in `Go`'s signature or locals — is reported by nothing in T15. (T16 still reports it wherever `Go` sits outside the owning set, which is why this was minor rather than a hole.) Limb (ii) closes it at the call site, and it costs nothing: `MemberUse.Signature` is already in the model.
- A **method** is container-facing if its own signature **or one of its locals** names one of exactly five types: `Microsoft.Extensions.DependencyInjection.IServiceCollection`, `Microsoft.Extensions.DependencyInjection.ServiceDescriptor`, `System.IServiceProvider`, `Microsoft.Extensions.Hosting.IHostApplicationBuilder`, `Microsoft.AspNetCore.Builder.WebApplicationBuilder`. Exact names, in one place, extended by a reviewable diff. `System.IServiceProvider` is on the list for a specific reason: a factory-lambda registration compiles to a method with signature `(IServiceProvider) -> SalesDbContext`, which is how `services.AddScoped(sp => …)` handing back a context is reached at all.
- **Limb (ii) does not close FOLLOWUP-024**, and an implementer should not read it as having done so. It does make `Microsoft.Extensions.Hosting.HostApplicationBuilder::get_Services` (signature `() -> IServiceCollection`) container-facing wherever it is called. But FOLLOWUP-024's escape is the `ldtoken` form of violation (a), which applies only *inside a container-facing **method***, and a method holding only a `HostApplicationBuilder` — the concrete class, which is not on the five-name list — is still not one. The row stands as written.
- **The site of a report** is the enclosing method **and** the called member, both named — so "reported at (d)'s call site" in §4.1.2 step 2 means the report names the instantiating method *and* `TypeHelper`1<FixtureTenantDbContext>::Register`, and a report naming only one of the two does not satisfy the assertion.
- Population (counted): container-facing call sites plus container-facing methods. **Floor on the integration branch after B-05: at least 5 call sites and at least 2 methods.** The call sites: three into `Microsoft.Extensions.Hosting` from `src/hosts/Aurora.Worker/Program.cs` (`Host.CreateApplicationBuilder`, `HostApplicationBuilder.Build`, `HostingAbstractionsHostExtensions.Run`) — a count the reviewer of this ADR measured with the scanner and I re-read in the source — plus `services.AddDbContext<CatalogDbContext>(…)` in `Aurora.Platform.Tenancy.CatalogServiceCollectionExtensions`; plus, by **limb (ii)**, `Microsoft.AspNetCore.Builder.WebApplication::CreateBuilder` called from `Aurora.Web.Program::Main`, whose signature `(String[]) -> WebApplicationBuilder` names the fifth surface type as its **return** type while its declaring type is under neither listed namespace. A re-scan of all nine production assemblies found it is the only member of that shape today. The methods: `AddCatalogDatabase` (its signature names `IServiceCollection`) and `Aurora.Web.Program.Main` (its `WebApplicationBuilder` local). **Limb (ii) is worth exactly one call site today, and that one is load-bearing.** An earlier draft of this bullet claimed it added nothing, reasoning only about project helpers — `AddCatalogDatabase` indeed has no caller yet, `Aurora.Composition` holding only a `.csproj` — and missed the framework member above. The claim was measured rather than believed, which is the only reason this floor is 5. It matters for the same reason the last one did: **at a floor of 4, deleting limb (ii) takes the population 5 → 4 and passes green**, so the floor would not detect the loss of the limb this section exists to add. The count rises again when `AddCatalogDatabase` acquires a caller (B-06). The implementer sets the inventory floor to the number the rule actually reports when it lands, and **a number below those is a rule narrower than this ADR specifies** — that is the check, not the guess.
- **Violation (a) — it names a context.** A container-facing call whose generic arguments, whose **declaring type's** generic arguments, or whose signature name a tenant context; or any mention of a tenant context anywhere inside a container-facing method — locals, `ldtoken` operands (`typeof(SalesDbContext)`), generic arguments. The declaring-type clause is what catches `TypeHelper<SalesDbContext>.Register(services)`, and it is the clause that requires §4.1.1a.
- **Violation (b) — it registers something the rule cannot see.** A container-facing call whose generic argument is a type parameter (`!0`, `!!0`) is judged **at the call sites that instantiate the enclosing generic declaration**, which §4.1.1a makes visible. If the production population contains **no** call site supplying a concrete argument for that declaration, the call is reported as an unresolved registration. The rule never says "examined, found nothing" about a registration whose subject it could not resolve.
- **Deliberately not a violation:** a `!0` inside a generic helper body whose call sites *are* visible. Banning that outright would make the ordinary `AddModule<TModule>(services) => services.AddScoped<TModule>()` a violation, and a rule that fires on the idiomatic shape gets widened in review rather than obeyed.
- Consequence for the executed attacks, each naming the limb that fires: `AddScoped<SalesDbContext>()` — **limb (i)**, the declaring type is under the DI namespace; `RegisterContext<SalesDbContext>(services)` — **limb (ii)**, the called member's signature names `IServiceCollection`; `TypeHelper<SalesDbContext>.Register(services)` — **limb (ii)**, plus its declaring type's generic argument naming the context, which is the part that needs §4.1.1a. Where the enclosing method is itself container-facing, the method limb reports the same call as well; that is overlap, not a second mechanism, and the report names the same site either way.

#### 4.1.1a The one scanner capability this ADR adds

Decision 2 and T15's violation (a) both require something today's scanner throws away, so it is specified here rather than discovered during implementation.

**What is missing.** `AssemblyScanner.NameOfTypeHandle`'s `TypeSpecification` case decodes the signature and then trims the rendered name at the first `<`, deliberately, because base-type and interface rules match the *open* type. Every instruction operand inherits that trim, so `TypeHelper<SalesDbContext>` reaches the rules as `TypeHelper\`1` and the context name is in no operand at all. The reviewer of this ADR compiled the shape and confirmed it: `generic=[] MENTIONS-TARGET=False`.

**The extension, about ten lines.** Keep the trimmed string for the rules that want the open type; **carry the full decode alongside it.** `MemberUse` gains a `DeclaringTypeUse` of type `TypeUse` — from `reader.GetTypeSpecification(handle).DecodeSignature(TypeUseProvider.Instance, null)` for a `TypeSpecification` (whose `Names` set already contains the flattened whole names), and `TypeUse.Named(name)` for a `TypeDefinition` or `TypeReference`. `TypeReferences.In` then yields that `TypeUse` for the declaring type instead of `TypeUse.Named(member.DeclaringType)`, which today re-narrows it. No rule loses anything: `DeclaringType` keeps its present meaning and its present callers.

**What demonstrates the extension failing.** A `TypeUse`-level test asserting that the declaring type of a call into `TypeHelper<FixtureTenantDbContext>` has both `TypeHelper\`1` and the context in its `Names`; and the fixture in §4.1.2 step 1(d). Restore the trim, or leave `TypeReferences.In` narrowing the declaring type, and both go red. If neither test exists, the extension is not done — a scanner change with no failing case is the same defect as a rule with no failing fixture.

**What it still cannot see.** A generic declaration instantiated only by reflection (`MakeGenericType`), and any type named only in a string. Those are §7 conventions, and violation (b) is what stops them being *silent*: a registration whose subject the rule cannot resolve is reported rather than counted as clean.

#### 4.1.2 What a reviewer does to prove the rules catch the helper form

Not "read the rule and agree". Four steps, each producing output:

1. Add to the violations fixture assembly, compiled by the real compiler: (a) `s.AddScoped<FixtureTenantDbContext>()`; (b) the **generic-method** helper `public static IServiceCollection AddTenantDbContext<TContext>(this IServiceCollection s) where TContext : DbContext => s.AddDbContext<TContext>();` **and** a separate call site `services.AddTenantDbContext<FixtureTenantDbContext>()`; (c) `services.Add(ServiceDescriptor.Describe(typeof(FixtureTenantDbContext), typeof(FixtureTenantDbContext), ServiceLifetime.Scoped))`; (d) the **generic-type** helper `public static class TypeHelper<TContext> { public static IServiceCollection Register(IServiceCollection s) => s.AddScoped<TContext>(); }` **and** a call site `TypeHelper<FixtureTenantDbContext>.Register(services);` in a different fixture assembly — this is the shape that walked past the first draft of this ADR, and it is the one to run first; (e) a factory lambda `services.AddScoped(sp => Open(sp));` where `Open` returns a `FixtureTenantDbContext`; (f) an **orphan generic registrar** — `internal static class OrphanRegistrar { internal static void Register<TContext>(IServiceCollection s) where TContext : DbContext => s.AddScoped<TContext>(); }` with **no** call site anywhere in the population supplying a concrete argument. (f) names no tenant context and is not supposed to: it is the fixture for violation (b), whose subject is *unresolvability*, not the context.
2. Run the rules and read the counts, **and assert the site and the clause of every expected report, not merely that some report exists.** T2 must report (b)'s *helper body*. T15 must report (a); (b)'s *call site*; (c); (d)'s *call site* under **violation (a)**, and **not** (d)'s helper body; (e)'s lambda; and (f)'s body under **violation (b)**, stating that no concrete instantiation of `OrphanRegistrar.Register<>` was found. The output must also state how many call sites were examined, not only how many violations were found. The site-and-clause assertion is what makes fault 1 below able to fail — see B-04's own finding l-1, an inertness test that asserted *a* violation rather than *the* violation.
3. Break one thing at a time, and watch a *specific* assertion go red. Each fault below isolates one mechanism, and the sentence after it says what the red proves:

   - **Fault 1 — restore `NameOfTypeHandle`'s trim (or let `TypeReferences.In` re-narrow the declaring type), i.e. remove §4.1.1a.** Expected: (d)'s **call-site** report under violation (a) disappears, **and (d)'s helper body is newly reported** under violation (b), because no concrete instantiation of `TypeHelper<>` is visible any more. **The total violation count barely moves — the report migrates.** That is precisely why step 2 asserts site and clause: a test that only asked "is (d) reported?" stays green with the extension gone, which is the trap this fault exists to spring. *What the red proves:* the extension is what turns "a registration here whose subject I cannot resolve" into "this call site registers `FixtureTenantDbContext`" — and, read the other way, that violation (b) is the net that stops the trim being silent.
   - **Fault 2 — delete violation (b).** Expected: **(f) alone** stops being reported; (d), with the extension intact, is still reported under violation (a), and every other expectation in step 2 is unchanged. *What the red proves:* a registration whose subject the rule cannot resolve is reported rather than counted as clean. Note the fixture this needs: a **generic** registrar with no visible concrete instantiation. A non-generic wrapper does not work — it still contains the concrete instantiation, so the call is reported under violation (a) and clause (b) is never reached, which is how the first version of this step failed to test anything.
   - **Fault 3 — narrow T15's container surface to the `AddDbContext` member name alone.** Expected: **every** report goes — (a), (b)'s call site, (c), (d)'s call site, (e) and (f) — because `AddScoped`, `ServiceDescriptor` and the lambda all leave the surface with it. The examined **count** collapses with them, from the §4.1.1 floor to roughly one. *What the red proves:* two things, and they are separable — that the surface rather than the member name is the key, and that the inventory floor is load-bearing, because the floor assertion fails here even before any missing report is noticed.
   - **Fault 4 — restore T2's member-name key and drop its call-site key.** Expected: (b)'s helper body stops being reported by T2. *What the red proves:* T2 judges the site, not the argument.

4. Restore, re-run, confirm the suite is green with the same counts as step 2.

Step 3 is the acceptance criterion. A rule whose fixture nobody has watched fail is not evidence.

#### 4.1.3 What a module writes instead — the ban must not be a dead end

A module needs no registration that names its context:

- **Handlers** take `ITenantDbContextFactory<SalesDbContext>` as a constructor parameter (ADR-0007 §4.5). Nothing registers it: the open generic in `Aurora.Platform.Tenancy` serves every closed instantiation.
- **Per-context configuration** (compiled model, interceptors, `HasDefaultSchema`) belongs to a per-module type that names its own context *in its own constructor or body* — inside the module's own assemblies, where §4.2 permits it — and is registered by its **own** name: `services.AddSingleton<IModuleContextConfiguration, SalesContextConfiguration>()`. No tenant context appears in a container-facing member.
- **Schema migration** (ADR-0027 §3): `SalesSchemaMigrator : IModuleSchemaMigrator` takes `ITenantMigrationContextFactory<SalesDbContext>` in its constructor and is registered by its own name. ADR-0027 §3 already forbids the runner from naming module contexts; this is the module-side half of the same statement.

If B-06 finds a case none of these cover, the answer is a new ADR naming that case — not a helper.

---

### 4.2 Decision 2 — **yes: a member that hands out a tenant `DbContext` is a violation.** The rule is the combination of *type*, *assembly* and *effective accessibility*, plus a construction clause — not any one of them alone.

A tenant `DbContext` is **owned**. Its owning assemblies are derived, not listed: the assembly that declares it, plus — when that assembly's name ends in `.Application` — the sibling assembly with `.Application` replaced by `.Infrastructure` (`solution-layout.md` §2.1 puts the context in `.Application` and its migrations in `.Infrastructure`). The derivation uses exact names. A context declared elsewhere (a platform context such as a future audit context) simply has a one-assembly owning set. **The derivation is the one key in this ADR that widens without a diff to any rule's data** — a new project named `<module>.Infrastructure` joins an existing owning set by being created. That is weaker than §2's standard and is recorded as such in §7; the containment is that creating a project inside an existing module's name is itself a reviewable event, and that the rule asserts the derived sibling exists rather than assuming it.

**T16 (new) — a tenant `DbContext` type is named only inside its owning assemblies.** Key: **assembly, exact.**

- Population (counted): (tenant context, production assembly) pairs outside the owning set.
- Violation: any mention of the context's full name — base type, interface, field, property, parameter, return, local, or any instruction operand, declaring type, signature or generic argument — in an assembly outside its owning set.
- **This clause is not implementable without §4.1.1a and must not ship before it.** Today the declaring type of an instruction reaches the rules with its generic arguments trimmed off, so `TypeHelper<SalesDbContext>.Register(services)` in `Aurora.Composition` mentions the context nowhere the rule can see. A T16 written against today's model would report nothing on the exact shape it exists to catch, in green — which is how this ADR's first draft came to state a clause it could not deliver.
- This closes the executed factory-door attack whenever the door is outside the module, and every registration from `Aurora.Composition`, `Aurora.Web` or `Aurora.Worker`, and `typeof(SalesDbContext)` anywhere else, with one key.
- It matches whole names, so EF Core's generated `SalesDbContextModelSnapshot` and `SalesDbContextModel` are different names and are not false positives; `[DbContext(typeof(SalesDbContext))]` is an attribute and is invisible to the scanner either way.

**T17 (new) — no externally reachable member yields a tenant `DbContext`.** Key: **effective accessibility, which no name can forge.**

- Effective accessibility = the member's own accessibility **and** the visibility of every enclosing type. `public` on an `internal` type is not externally reachable.
- Population (counted): externally reachable members in production code (solution-wide; a large, never-zero number).
- Violation: an externally reachable method (including a property accessor, which is a method in metadata) whose **return type** names a tenant context, or an externally reachable **field or property** whose type names one — unless the same type use also names `ITenantDbContextFactory` or `ITenantMigrationContextFactory`, which is how a handler's `ITenantDbContextFactory<SalesDbContext>` member is distinguished from a member that hands out the context itself.
- A **by-value** parameter typed as a tenant context is **not** a violation: the caller already holds one. A **`ref` or `out`** parameter **is** one, because it yields a context rather than receiving it — `public static bool TryOpen(out SalesDbContext context)` on a public type is the executed door with a different signature, and inside an owning assembly nothing else reports it (T17 is the wrong rule there by design and T18 sees no `newobj` if the context came from the factory). Metadata distinguishes the two without ambiguity: a by-ref parameter decodes as `SalesDbContext&` and keeps the element name, and `out` versus `ref` does not matter here because both hand a context to the caller.
- **The exclusion term is the one place a name is load-bearing, and it is bounded.** Excluding a member because its type "names `ITenantDbContextFactory`" is an exclusion keyed on a simple name, and §2 says a violator can mint one. The distinction that makes this acceptable *temporarily*: a too-wide **subject** match produces false positives, which fail loudly and are fixed; a too-wide **exclusion** produces false negatives, which are silent. So: simple-name matching is acceptable for the subject sets B-04 already matches that way (`TenantScope`, `TenantDatabaseHandle`, the factory interfaces) while B-06 has not fixed their namespaces, but **T17's exclusion must be the two exact full names, and the change that declares `ITenantDbContextFactory<>` must supply them** — with the T20 existence check applied to the excluded names, so an exclusion that resolves to no type fails rather than excluding nothing quietly. Until then T17 runs with no exclusion term at all and the handler fixture of §4.2.2 step 3 is expected to be reported: a documented false positive is preferable to an exclusion nobody has verified.
- **The sanctioned factory is not exempted; it is not matched.** `ValueTask<TContext>.CreateAsync` returns a type parameter, and a type parameter is not a tenant context's full name. If `Aurora.Platform.Tenancy` ever declares a non-generic member returning a concrete context, T16 reports it (tenancy is outside every module's owning set) and T17 reports it too. That is the intended behaviour and it needs no extra clause.

**T18 (new) — a tenant `DbContext` is constructed only in `Aurora.Platform.Tenancy`.** Key: **the `newobj` opcode plus the exact assembly.**

- Population (counted): tenant `DbContext` types.
- Violation: a `newobj` naming a tenant context in any production assembly other than `Aurora.Platform.Tenancy`.
- This is the clause that closes the door *inside* the owning module, where T17 is silent by design, and it is also what catches `new SalesDbContext(options, null!)` — the one construction the C# nullable analysis will not stop.

#### 4.2.1 The honest boundary of Decision 2

Inside an owning assembly, a member that obtains a context **from the factory** and passes it to another type in the same assembly is reported by nothing — and it is not a bypass: to call the factory the caller must already hold a `TenantScope`, which ADR-0007 §3.4 makes unforgeable. The bypass inside an owning assembly is *construction*, and T18 covers it. This sentence exists so that no rule's documentation can later claim T17 covers the internal case; it does not, and the executed fixture `internal static class PublicFactoryDoor` must be recorded as a **T18** finding, never as a T17 one.

#### 4.2.2 What a reviewer does to prove these rules fire

1. Fixtures, in a population that spans **two assembly names** — the re-review's finding m-3 proved a single-assembly fixture cannot exercise a cross-assembly clause, and T16 is entirely a cross-assembly clause. Either a second fixture assembly or hand-constructed `ScannedType` records with two distinct `AssemblyName`s.
2. Positive fixtures: a public factory door outside the owning set (T16); `public static class Door { public static FixtureTenantDbContext Open() … }` (T17, return type); **`public static class RefDoor { public static bool TryOpen(out FixtureTenantDbContext context) … }` (T17, by-ref parameter)** — the return type is `bool`, so this fixture is reported only if the by-ref clause exists, and the report must name the *parameter* as the site; `internal static class Door { public static FixtureTenantDbContext Open() => new(options, null!); }` (T18, and **not** T17).
2a. Negative fixture for the same clause, asserted as negative: `public static void Use(FixtureTenantDbContext context)` on a public type — a **by-value** parameter — must **not** be reported. Without it the clause could be widened to "any parameter" and every handler that takes a context would be reported, which is the failure mode a positive-only fixture cannot see.
3. The handler fixture — an externally reachable member typed `ITenantDbContextFactory<FixtureTenantDbContext>` — is asserted **in whichever direction the exclusion term is in at the time**, and the assertion states which: *before* B-06 supplies the exact interface names there is no exclusion term and the fixture **must** be reported (a documented false positive, asserted so that it cannot go unnoticed); *after*, the fixture **must not** be reported, and dropping the exclusion term must turn that assertion red. An assertion that flips silently when B-06 lands is the thing to avoid, so the fixture's test name says which phase it is asserting.
4. Faults that must turn a fixture red, one mechanism each:

   - make T16's owning set a prefix match — a `…Sales.Evil` fixture stops being reported;
   - make T17 read declared accessibility instead of effective accessibility — the T18 fixture, a `public` member on an `internal` type, starts being reported by T17, which the step-3 assertion catches in either phase;
   - **drop T17's by-ref term, keeping return types, fields and properties** — `RefDoor.TryOpen` stops being reported. **T17's examined count does not move**: the population is externally reachable members, and it is the same members either way. A healthy count is exactly what a missing clause hides behind, which is why this clause needs its own fixture and this fault rather than a number;
   - **widen T17's parameter term to all parameters** — `Use` starts being reported and the step 2a assertion goes red;
   - restrict T18 to a member-name key — the `newobj` fixture stops being reported.

### 4.3 Decision 3 — **the catalog context is identified by full name *and* assembly name, and a second type with the same simple name is a violation, not an exemption.**

- The exempt pair is exactly `("Aurora.Platform.Tenancy.Catalog.CatalogDbContext", "Aurora.Platform.Tenancy")` (B-05, `src/platform/Aurora.Platform.Tenancy/Catalog/CatalogDbContext.cs`).
- **T19 (new, and small) — the catalog exemption is unique and lands where it says.** Population (counted): production types whose base chain reaches `Microsoft.EntityFrameworkCore.DbContext`, **computed directly and not through `TenancyNames.TenantContextsIn`** — that helper subtracts the catalog by simple name, which is the exemption under test. Two violations: (a) a type whose simple name is `CatalogDbContext` that is not the exempt pair; (b) **if the population contains any type deriving from `DbContext` at all, the exempt pair must be present exactly once.** Clause (b) is the one that makes a rename fail loudly instead of silently turning every tenant-context rule's exemption into a no-op.
- **Clause (b) is self-triggering, and it has already triggered.** It was written against a population that was empty when this ADR was drafted; **B-05 merged on 2026-09-11**, so `Aurora.Platform.Tenancy.Catalog.CatalogDbContext` is on the integration branch and clause (b) is **live from the moment it is implemented** — a rename of that type now fails the rule rather than waiting for someone to promote anything. **It must not cite `RuleInventoryTests.No_tenant_DbContext_exists_yet_which_is_why_T1_is_inert` as its wake-up** (that is the current name on `task/B-04-rework2`; the original guard has since been split in two): the guard runs through `TenancyNames.TenantContextsIn`, which subtracts the exempt pair, so the catalog landing leaves it green — correctly, for what *that* test measures, and uselessly as a wake-up for this one. A wake-up that depends on a human reading a date is not a mechanism, and citing one that cannot fire is the defect this ADR exists to stamp out.
- **Demonstration:** a `…Violations.Attack.CatalogDbContext` deriving from `DbContext` with a public constructor must be reported by T1 **and** by T19(a). Revert the exemption to simple-name matching and both reports disappear: that is the fault that must turn the fixture red. Rename the real catalog context in a scratch copy and T19(b) must go red.
- **Adoption status (2026-09-11): this decision is built.** `task/B-04-rework2` carries it as `TenancyNames.NonTenantContext(FullName, AssemblyName)` with the single entry `CatalogContext`, exercised by `T1_stays_silent_on_the_catalog_context_as_the_exact_full_name_and_assembly_pair`, `T1_fires_on_a_context_merely_named_CatalogDbContext_outside_the_catalog_namespace`, `T1_fires_on_the_catalog_context_at_the_right_full_name_but_in_the_wrong_assembly` and `The_only_context_exempt_from_the_tenancy_rules_is_the_catalog_as_one_exact_pair`. What is **not** built is clause (b) — the presence check — and T19 as a named rule with its own count. That is the remainder, and it is small.
- **Why not an attribute:** the scanner cannot read attributes (§1.1), and a self-applied mark is not a boundary (§2).

### 4.4 Decision 4 — **allow-lists match exact assembly names. Never a prefix. Every entry must name an assembly that exists.**

- Both lists become exact sets of **two** entries, and each entry exists for named types:

| Entry | Why it is on the list |
|---|---|
| `Aurora.Platform.Tenancy` | Implements `ITenantDbContextFactory<>` and `ITenantMigrationContextFactory<>` (ADR-0007 §4.1, ADR-0027 §1); opens and disposes the DDL connection behind `ITenantAdminConnectionFactory` (ADR-0027 §2) |
| `Aurora.Platform.Tenancy.Contracts` | **Declares** `TenantAccess`, `TenantScope`, `TenantDatabaseHandle` and both factory interfaces (ADR-0007 §3.4, ADR-0027 §1). Without this entry T6 reports the declaring assembly of the very type it guards on the day it lands — and the cheapest fix on that branch is to widen the list back to a prefix, undoing this decision |

- The second entry is **not** a guessed name and does not contradict the paragraph below: the assembly is named by ADR-0007 §3.4 and ADR-0027 §1, and **since B-05 merged on 2026-09-11 it exists on the integration branch** (`src/platform/Aurora.Platform.Tenancy.Contracts`), as does the first. Both entries name assemblies that are there today. What is refused is entering a name for an assembly no ADR names and no branch has created.
- ADR-0027 §1's "the provisioning/migration runner" assemblies are therefore **not** pre-entered. The task that creates such an assembly adds its exact name to the list **in its own diff**, which is what "extending it is a reviewable diff" was always supposed to mean.
- **T20 (new, and smaller) — every allow-list entry names an assembly in the production population.** Population (counted): allow-list entries across all allow-listed rules. A renamed, moved or deleted allow-listed assembly turns this red rather than silently widening the rule it guards, and a typo in a new entry fails on the branch that adds it.
- **T20 is live, with a floor of 2 — the condition this ADR set for it has been met.** When this was first written `src/platform/` held only a `README.md`, so T20 was specified inert with a guard asserting the absence of both assemblies, precisely because a rule that is red on its own implementation branch invites an "unless it does not exist yet" escape. **B-05 merged on 2026-09-11 and both assemblies are now in the production population**, so T20 lands live: two entries, both resolvable, floor 2. The inert specification and its guard are kept in this paragraph as history, not as instructions — an implementer reading this today writes the live rule.
- **Adoption status (2026-09-11): this decision is *not* built yet, and the code says so.** `task/B-04-rework2` carries a **segment-bounded prefix** (`TenancyNames.TenancyAssemblyPrefix` with `IsWithin`), documented in its own remarks as *"Interim, pending ADR-0032 §4.4 … Whoever implements the ADR replaces this, and the tests that pin it, with the exact set."* It refuses the executed `Aurora.Platform.TenancyBypass` attack and admits the contracts assembly, so it is strictly better than the plain prefix it replaced — but `Aurora.Platform.Tenancy.Anything` still authorises itself one segment further down, and T20 does not exist. **The remainder is a task, not a disagreement:** replace the prefix with the two exact names, replace the tests that pin the prefix (`The_tenancy_allow_list_prefix_is_segment_bounded`, `T3_stays_silent_inside_the_tenancy_contracts_assembly`, `T6_allows_the_tenancy_assembly_and_the_segments_below_it_and_nothing_that_merely_starts_with_it`), and add T20. Recorded here so that no reader of this ADR believes the mechanism is in place when it is not.
- **Demonstration:** hand-constructed `ScannedType` records in assembly `Aurora.Platform.TenancyBypass` — one implementing `ITenantDbContextFactory\`1`, one naming `TenantDatabaseHandle` — must be reported by T3 and T6 respectively; a record in `Aurora.Platform.Tenancy.Contracts` declaring `TenantDatabaseHandle` must **not** be. Restore `StartsWith` and the first two reports disappear. For T20, run it over a hand-built (allow-list, population) pair with one entry missing and watch it report; and, now that both assemblies exist, rename `Aurora.Platform.Tenancy` in a scratch copy and watch the live rule go red.

## 5. Rule summary

**None of the rules below is the guarantee.** The guarantee is ADR-0007 §4.1 layer 1: one `internal` constructor taking a `TenantAccess` that only `Aurora.Platform.Tenancy` can construct. These rules are defence in depth over it, each with a stated blind spot in §7; their value is that an attempt becomes visible in review, not that they are individually impassable. Read that sentence before citing this table as coverage.

| Id | Rule | Keys on | State when it lands |
|---|---|---|---|
| **T2** *(amended)* | The `AddDbContext` family is called only in `Aurora.Platform.Tenancy`, only for the catalog context; an unresolved generic argument is a violation | Call-site assembly + argument full name | **Live** — B-05 merged 2026-09-11 and `AddDbContext<CatalogDbContext>` is on the integration branch, so the floor is ≥ 1. B-04's own guard `The_tenancy_assembly_does_not_exist_yet_which_is_why_T2_is_inert` expires on that merge, which is the expiry mechanism working rather than a defect |
| **T15** *(new)* | No container-facing call or method names a tenant `DbContext`, and no container-facing call registers a type the rule cannot resolve | **Segment-bounded namespace prefix** (`Microsoft.Extensions.DependencyInjection`, `Microsoft.Extensions.Hosting`) for a call's declaring type, **five exact type names** matched in a called member's signature, or in a method's own signature **or locals** — see §4.1.1 | **Live, floor 5 container-facing call sites and 2 container-facing methods** — the exact merged population (§4.1.1), measured from a Release build of the integration branch: three `Microsoft.Extensions.Hosting` calls in `Aurora.Worker/Program.cs`, `AddDbContext<CatalogDbContext>` in `Aurora.Platform.Tenancy`, `WebApplication.CreateBuilder` in `Aurora.Web/Program.cs` (limb (ii), by return type), and the methods `AddCatalogDatabase` (signature) and `Aurora.Web.Program.Main` (local). Finds nothing until B-06. Violation (a) needs the §4.1.1a extension |
| **T16** *(new)* | A tenant `DbContext` is named only inside its owning assemblies | Assembly, exact, derived from the declaring assembly (the one derivation that widens without a rule diff — §7) | Inert until the first tenant context; fixture + inventory row. **Requires the §4.1.1a scanner extension**, without which its "any mention … declaring type" clause is not implementable |
| **T17** *(new)* | No externally reachable member yields a tenant `DbContext` — return type, field, property, or a `ref`/`out` parameter | Effective accessibility (member + enclosing type visibility) | Live today; floor is the count of externally reachable members |
| **T18** *(new)* | A tenant `DbContext` is constructed only in `Aurora.Platform.Tenancy` | `newobj` + exact assembly | Inert until the first tenant context |
| **T19** *(new)* | The catalog exemption is one exact (full name, assembly) pair and nothing else carries that simple name | Full name + assembly name | **Live** — the catalog context is on the integration branch since B-05, so clause (b) bites from the moment it is implemented, with no promotion step. Clause (a) and the exact-pair exemption are **already built** on `task/B-04-rework2`; clause (b) and the named rule are the remainder (§4.3). Must **not** cite the `No_tenant_DbContext_exists_yet…` guard, which cannot fire on it |
| **T20** *(new)* | Every allow-list entry names an assembly that exists | Exact assembly names | **Live, floor 2** — B-05 brought both allow-listed assemblies, so the condition this ADR set for T20 is met. The exact lists themselves are **not yet built**: `task/B-04-rework2` carries a documented interim segment-bounded prefix pending this decision (§4.4) |

**A floor is not a formality, and this table shipped a proof of it.** Two reviews ago this row said `floor 3` while §4.1.1 said four call sites and two methods. Three is exactly what the `Microsoft.Extensions.Hosting` calls in `Aurora.Worker/Program.cs` supply on their own — so a T15 shipped **without the entire `Microsoft.Extensions.DependencyInjection` limb**, the limb that catches `AddScoped<SalesDbContext>()` and therefore the bypass this ADR exists to close, would have passed its own floor green. A floor set below the narrowing it is supposed to detect detects nothing. Set each floor from the measured population, not from the part of it you happened to enumerate first — and **measure it again after widening the rule**: this floor was wrong a second time, at 4, because the limb added in the same rework matched a framework member nobody had thought to count, and 4 would have let that limb be deleted in green. Both mistakes are the same one: a floor inherited from an enumeration rather than taken from a measurement.

Every **live** rule above carries an inventory row with a **non-zero floor** and a `SubjectKind` naming what it counted; every **inert** rule carries a row naming the task that wakes it, a guard that expires on a fact rather than a date, and a fixture proving it still fires (ADR-0030, `RuleInventoryTests`). A rule that reports "no violations" without a count is the defect this project has rejected three times — and an inert rule whose wake-up cannot fire is the same defect wearing a different hat, which is what M-4 of this ADR's own review caught.

## 6. What this ADR does **not** decide

Named here so that nobody reads silence as permission, and so the follow-ups are not rediscovered:

1. **How `ITenantDbContextFactory<TContext>` actually constructs a context** whose constructor is `internal` to another assembly (reflection, `InternalsVisibleTo`, or a registered per-module construction delegate). B-06's decision; T18 holds whichever way it goes, because the factory is generic and names no concrete context.
2. **Whether a fitness rule confines connection-string and `NpgsqlDataSource` construction to the resolver** (`modules.md` §4 asserts it in prose; no rule id exists). That is the backstop for reflective construction. **Routed to the project-manager in this branch's summary** as a backlog row rather than left here.
3. **Who allocates tenancy rule ids.** This ADR does not invent a scheme; it consumes the range **T15–T20**, allocated to this branch by the orchestrator's file-and-id partition, and renumbers nothing outside it. The unresolved situation it is *not* deciding: `testing-strategy.md` §5.3's T6 ("`TenantScope` in no serializable payload") is not the implemented T6 (ADR-0027's `TenantDatabaseHandle` allow-list); T7/T8 in that table are unimplemented; and `task/ARCH-IDENTITY` claims T9 and T10 for a company-scope rule and a `HybridCache` key rule. **The first draft of this ADR took T9–T14 and reproduced the exact defect it records here** — the reviewer caught it. Someone needs to own the id space, not just the next free number.
4. **Tightening the rest of the simple-name subject matching** in `TenancyNames` (`TenantScope`, `TenantDatabaseHandle`, `TenantAccess`, both factory interfaces) to full names once B-06 fixes the namespaces. It is safe today for the reason in §4.2 — a wide subject match fails loudly — but it is a name-keyed match and it should not stay one forever. **Routed to the project-manager in this branch's summary** as a backlog row.
5. **The narrow reflective-construction rule.** "A call to `System.Activator::CreateInstance` or `System.Reflection.ConstructorInfo::Invoke` in a method that also names a tenant context" is writable against today's model — the scanner records both declaring types — and it would catch the common shape of the §7 convention below. It has no id here because T15–T20 is the whole range allocated to this branch, and it is not folded into T18 because T18's population is `newobj` sites and a second population in one rule is how a clause goes silent behind a healthy count. Needs an id and an owner.
6. **How a tenant `DbContext`'s migrations are scaffolded at design time under T18.** B-05 merged `Aurora.Platform.Tenancy.Catalog.CatalogDesignTimeDbContextFactory`, which does `return new CatalogDbContext(options.Options)` — legal, because the catalog is exempt and the type is inside `Aurora.Platform.Tenancy`. The module equivalent is not: `dotnet ef migrations add` wants an `IDesignTimeDbContextFactory<SalesDbContext>` in the module's own assembly, and that is a `newobj` of a tenant context outside `Aurora.Platform.Tenancy` — a T18 violation by design, not by accident. Whether the answer is a generic design-time factory in the tenancy assembly, a `dotnet ef` invocation that supplies one, or pre-generated SQL (ADR-0027's option C) is B-06/B-08's decision with an ADR, not this one's. Named here because the precedent is now merged and the first module will hit it.
7. **Whether L6** ("no `public` type in a module's `Application` or `Infrastructure`") **subsumes part of T17** once it is implemented. It probably narrows T17's population; it does not replace it, because T17 also covers platform assemblies.

## 7. What is a convention here, and not a rule

Stated plainly, because the defect three reviews have found in this repository is documentation that reads as though a mechanism exists.

| Gap | Why no rule catches it | What actually stands behind it |
|---|---|---|
| **Reflective construction or resolution inside an owning assembly** — `Activator.CreateInstance(typeof(SalesDbContext), …)`, `ConstructorInfo.Invoke`, `Type.GetType("…SalesDbContext")` | The general case is not mechanisable: a string-based lookup is an `ldstr` operand the scanner does not record (`AssemblyScanner.IsTokenOperand` excludes `InlineString`). The `ldtoken` half *is* visible but is indistinguishable from EF Core's legitimate uses inside the owning module | **Convention today — but only the general case.** The narrow form (a call to `Activator::CreateInstance` or `ConstructorInfo::Invoke` in a method that also names a tenant context) is a writable rule and is named as a follow-up in §6 item 5 rather than claimed here; this ADR's id range is spent. Reviewer's eye, Full tier, until that lands. Runtime backstop: the constructor takes a non-nullable `TenantAccess` only `Aurora.Platform.Tenancy` can construct, and the connection still has to come from somewhere (§6 item 2) |
| **A registration reached through a project-specific wrapper type** whose signature names no container-surface type, called from inside the owning module | T15's key is the container surface; a wrapper is not on it. T16 permits naming the context inside the owning module | **Convention.** The backstop is narrower than it looks and the earlier draft of this row overstated it: "the container cannot activate a tenant context" holds for *constructor* activation only. A factory-lambda registration — `services.AddScoped(sp => factory.CreateAsync(accessor.Current).Result)` — never touches the constructor and does hand out a context. What covers *that* shape is T15's `System.IServiceProvider` entry: the lambda compiles to a method with signature `(IServiceProvider) -> SalesDbContext`, container-facing by signature and naming a tenant context. The residue left to convention is a wrapper that is neither container-facing nor outside the owning module |
| **`null!` passed as the `TenantAccess` argument inside `Aurora.Platform.Tenancy`** | T18 permits construction there, which is the point of the assembly | **Convention.** Full-tier review of the tenancy assembly; ADR-0007 §4.1's "a reviewer will see it as a deliberate act" is the whole mechanism, and it is a human one |
| **The container-surface list itself** (§4.1.1) | It is a hand-kept list of framework type names; a container API outside those namespaces is not covered | **Half rule, half convention.** The list is data in the test and extending it is a diff, but nothing proves it is complete |
| **T16's owning-set derivation widens without a rule diff** | The set is computed from the declaring assembly's name, so a new project named `<module>.Infrastructure` joins an existing owning set by existing. No rule data changes, so no reviewer sees a widened rule — only a new project | **Half rule, half convention**, and weaker than §2's standard. Contained by two things: creating a project inside an existing module's name is itself a reviewable event in the solution file, and T20's existence check applies to the derived sibling, so a derivation naming an assembly that does not exist fails rather than silently covering nothing |

**None of these is the guarantee.** The guarantee is ADR-0007 §4.1 layer 1: one `internal` constructor taking an unforgeable `TenantAccess`. T2 and T15–T18 are defence in depth over that, and their value is that they make an *attempt* visible in review — not that they are individually impassable.

## 8. Consequences

- **Positive.** The two questions blocking B-06 are answered with mechanisms, not prose: B-04's placeholder predicate becomes "call site assembly ≠ `Aurora.Platform.Tenancy`", and B-06 knows before it writes a line that `AddTenantDbContext<T>()` is not on the table and what replaces it.
- **Positive.** Four bypasses close with keys that cannot be minted by the code they judge; the executed attacks A1, A2, A3, A7 and A9 all become reported violations with fixtures.
- **One scanner capability is added, and exactly one** (§4.1.1a, about ten lines): the declaring type of an instruction is carried as a `TypeUse` whose `Names` include its closed generic arguments. Every other key is something `ScannedModel` already exposes. An earlier draft of this ADR claimed *no* capability was added; that claim was false — the trim in `NameOfTypeHandle` made Decision 2's "any mention … declaring type" unimplementable — and it was exactly the defect this ADR exists to stamp out, in the ADR itself. The extension has its own failing demonstration, like any rule.
- **Negative.** That extension touches a file B-04 owns, so it must be sequenced with B-04's rework rather than dropped into it, and the rules that depend on it (T15 violation (a), T16) cannot land before it.
- **Negative.** Six new rules, one amendment and one scanner extension, each needing a fixture, an inventory row and a floor. Sizing is the project-manager's call; T2, T19 and T20 are corrections to rules B-04 already owns, while T15–T18 are new and mostly inert until B-06.
- **Negative.** T16 and T19 hard-code full names from B-05 and from the module naming convention. A rename fails the build. That is the intended cost of a boundary over a convention, and it is why both have a clause that fails *loudly* rather than silently exempting nothing.
- **Negative for ergonomics.** Module composition code is slightly more verbose: a per-module configuration type instead of one `AddTenantDbContext<T>()` line. §4.1.3 is the written justification, per `CLAUDE.md`'s rule that novelty — and here, deliberate inconvenience — needs one.

## 9. Revisit when

- EF Core introduces a registration shape none of §4.1.3's alternatives cover (a compiled model that must be registered per context, or pooling that genuinely pays for itself in this architecture). Then a new ADR names that case and the exemption it needs, keyed on an exact assembly.
