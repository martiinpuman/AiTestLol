# ADR-0028 — The tenant audit store: schema, append-only enforcement and the write path

- **Status:** Accepted (2026-09-11) — **amended 2026-09-11 (Amendment 1): §2 is replaced, and one Consequences bullet and one Options-table cell are corrected.** **Amended 2026-09-12 (Amendment 2): §2 mechanism 3's truncate half is replaced — the guard is attached to every partition, the `DEFAULT` partition included, by the same statement that creates or attaches it, instead of by a partition job that does not exist.** The decision — the `audit` schema, monthly partitioning, the write path and the hash chain — is unchanged by both.
- **Deciders:** architect
- **Supersedes:** ADR-0004 rule 5's table name (`platform.audit_event`), ADR-0007 §9.1's prose placing audit in the `platform` schema, and the same table name where it appears in ADR-0007 §11.5. Everywhere those documents say `platform.audit_event`, read `audit.audit_event`. ADR-0018's decisions are unchanged; this ADR fixes the mechanics it left to the implementer.
- **Superseded by:** —
- **Related:** ADR-0018 (audit, retention, erasure), ADR-0004 rule 5, ADR-0007 §4.3 / §9.2, ADR-0027 (`TenantAccess`), `../product/specs/SPEC-001-tenant-provisioning-and-first-login.md` BR-7/AC-6, `../reviews/B-05.md` finding M-1, the third security review of ADR-0029 (PR #5) finding M-1 — `../BACKLOG.md` `FOLLOWUP-026`

## Context

The project-manager could not find a bootstrap task that builds a tenant-side audit write path, and asked whether it is implicit in B-07.2's `platform` schema work. It is not, and three documents disagree about where the table even lives:

- ADR-0004 rule 5 names `platform.audit_event`;
- ADR-0007 §9.1 says the tenant `platform` schema holds "tenant identity, audit, outbox, settings, feature-flag overrides";
- ADR-0018 §1 and `../architecture/modules.md` §4 name `audit.audit_event` in a schema `audit` owned by an Audit module.

Meanwhile SPEC-001 BR-7/AC-6 requires an audit event **inside the new tenant** at provisioning, SPEC-002 BR-5 requires one for a business write, `CLAUDE.md` requires every financial change to be audit-logged, and nothing in B-01 … B-15 builds `IAuditWriter`, the table, the append-only enforcement or the hash chain. `src/platform/` contains no projects at all today. A walking skeleton that cannot write an audit event does not demonstrate the property this product is sold on.

The B-05 review (finding M-1) makes the risk concrete rather than theoretical: `ALTER DEFAULT PRIVILEGES` granted `aurora_app` `DELETE` on every future table in the catalog schema, so `catalog.operator_audit_event` — ADR-0007 §9.2's "append-only" operator trail — was provably deletable by the request-path role. An append-only table is append-only because of a mechanism, never because of its name.

## Options considered

| Option | Pros | Cons |
|---|---|---|
| **Own schema `audit`, privilege policy applied at schema granularity, plus a trigger** *(chosen — the pro is restated by Amendment 1; the second statement quoted here is a no-op and the corrected mechanism is a positive default grant)* | ~~`REVOKE UPDATE, DELETE ON ALL TABLES IN SCHEMA audit FROM aurora_app` **and** `ALTER DEFAULT PRIVILEGES … IN SCHEMA audit REVOKE UPDATE, DELETE ON TABLES FROM aurora_app`~~ A **schema-wide default privilege** makes a table added to that schema next year append-only by where it is created instead of by memory — `audit` can carry one because every table in it is append-only, and `platform` cannot; the trigger catches the owner role too | One more schema per tenant database |
| Audit table inside `platform` (ADR-0004 rule 5 / ADR-0007 §9.1 as written) | One fewer schema | `platform` also holds `outbox`, `setting`, `feature_flag_override`, `job_run` — all of which **must** be `UPDATE`/`DELETE`-able by `aurora_app`. A schema-wide append-only policy is therefore impossible there, and every append-only guarantee falls back to a per-table grant someone must remember. That is exactly the B-05 M-1 failure, pre-installed |
| Audit in a separate database per tenant | Physically separable retention | A second database to provision, migrate, back up and restore per tenant, and no transactional write with the change it records — which ADR-0018 requires |

## Decision

### 1. Location

`audit.audit_event`, in the **tenant** database, schema `audit`, owned by the Audit platform module (`modules.md` §4). ADR-0018 and `modules.md` were already right; ADR-0004 rule 5 and ADR-0007 §9.1 are corrected by this ADR. The columns are ADR-0018 §1's, unchanged.

### 2. Append-only: what enforces it, what only detects it, and what nothing here prevents

*(Replaced by Amendment 1, 2026-09-11. The original text of this section is quoted in the amendment, with what was wrong with it.)*

Every statement in this section was executed against `postgres:17-alpine` — **PostgreSQL 17.11**, the pinned image — on 2026-09-11, as `aurora_migrator` (the schema owner) and as `aurora_app` (the request-path role). Where a statement does nothing, that is recorded instead of the statement.

**Every probe connects as the role it is testing** — `aurora_app` for mechanisms 1 and 2, `aurora_migrator` for mechanism 3 — and executes the forbidden statement, rather than asserting that a `GRANT` or `REVOKE` ran. A probe that runs as the fixture's superuser proves nothing: that is the test that passed on B-05 while the table was deletable.

**1. Grant — for the table itself.** `aurora_app` ends the migration holding exactly `SELECT, INSERT` on `audit.audit_event`, and nothing else: no `UPDATE`, no `DELETE`, no `TRUNCATE`, no column-level grant. Whether that comes from an explicit `GRANT` or from mechanism 2's default applying to the `CREATE TABLE` is an implementation detail; **the assertion is on the resulting ACL, never on which statement ran.**

- *Demonstrated by* comparing the **ACL itself** against the recorded decision, for **every relation in schema `audit`, partitions included** — `aclexplode(pg_class.relacl)` plus `pg_attribute.attacl`, projected for `aurora_app` **and** `PUBLIC` — and then, connected **as `aurora_app`**, executing `UPDATE` and `DELETE` and expecting SQLSTATE `42501`.
- *Why the ACL and not `has_table_privilege`:* finding H-1 of `../reviews/security-B-05.md`, executed. A column-level `GRANT UPDATE (detail) ON … TO aurora_app` leaves `has_table_privilege(…, 'UPDATE')` returning false while the `UPDATE` succeeds, and PostgreSQL 17 added a table privilege (`MAINTAIN`) that a hand-written privilege list does not contain. A per-privilege oracle is a test that reports green while the table is writable.

**2. Default privilege — for a table added to the schema later.**

```sql
ALTER DEFAULT PRIVILEGES FOR ROLE aurora_migrator IN SCHEMA audit
  GRANT SELECT, INSERT ON TABLES TO aurora_app;      -- a positive grant, not a revoke
```

- *Why this form.* The `REVOKE` form this ADR originally specified does nothing at all. PostgreSQL's built-in default already grants `aurora_app` no privilege on a new table, so there is nothing to revoke: the statement succeeds, `pg_default_acl` stays **empty** (verified: `0 rows`), and a later ordinary `GRANT SELECT, INSERT, UPDATE, DELETE` on a new `audit` table is completely unrestrained (verified: `UPDATE t · DELETE t`). The positive grant does create the row — verified as `defaclacl = {aurora_app=ar/aurora_migrator}` — and it determines the ACL of the next table: a table created afterwards by `aurora_migrator` in `audit` came out `{aurora_migrator=arwdDxtm/aurora_migrator, aurora_app=ar/aurora_migrator}`, i.e. `SELECT` and `INSERT` for the app role and nothing more.
- *Demonstrated by* two assertions, both required: (a) `pg_default_acl` holds exactly one row for (`aurora_migrator`, schema `audit`, object type `r`) with that ACL; and (b) a table **created in `audit` after the migration has run** gives `aurora_app` exactly `{SELECT, INSERT}`, with an executed `INSERT` that succeeds and an executed `UPDATE`/`DELETE` that returns `42501`.
- *Why (b) must assert the positive half too.* A probe that only checks "`UPDATE` is refused on the new table" **passes against the no-op**, because a new table grants `aurora_app` nothing whatsoever. Asserting the exact set `{SELECT, INSERT}` fails in both directions: too little (the default-ACL row is missing, so the `INSERT` probe fails) and too much (someone widened it, so the `UPDATE` probe fails).
- *What it does not do.* A default ACL does not restrain a later explicit `GRANT`; nothing in PostgreSQL does. Grant drift is **detected** by mechanism 1's ACL comparison, not prevented. And the default applies only to tables created by `aurora_migrator`: a table created in `audit` by any other role gets no ACL entry for `aurora_app` at all (verified — `relacl` null, every privilege false), which is fail-closed rather than silently open.

**3. Trigger — against every ordinary DML path, including the owner.** A `BEFORE UPDATE OR DELETE … FOR EACH ROW` trigger on the partitioned parent `audit.audit_event`, raising `42501`.

- *Verified:* the trigger can be created on a partitioned parent; it is **cloned to a partition created afterwards** (`CREATE TABLE … PARTITION OF` produced a partition carrying the trigger); and it raised for `aurora_migrator` — the owner, whom privileges do not restrain — both through the parent and against the partition directly. **Amended by Amendment 2 (2026-09-12): the clone is not enough.** `ALTER TABLE … DETACH PARTITION` **deletes cloned triggers**, so a row guard that exists only by clone is absent for as long as a partition is detached — executed, `DELETE` succeeded on the detached table and `ATTACH` restored the clone, leaving no trace. The row guard is therefore created **on each partition** by the same migration step that creates or attaches it, exactly like the truncate guard, and both are enabled `ALWAYS`. **It must carry a different name from the parent's**, because the clone owns that name and cannot be dropped, and it is identified by `tgparentid = 0` — see Amendment 2 part 1, which is where that was executed.
- *Plus* a `BEFORE TRUNCATE … FOR EACH STATEMENT` trigger on the parent **and on every partition, the `DEFAULT` partition included, created by the same migration statement that creates or attaches the partition** — **replaced by Amendment 2 (2026-09-12); the original sentence, which reached only partitions created by a job that does not exist, is quoted there with what was wrong with it.** The verified limitation it rests on is unchanged: **truncate triggers are not cloned to partitions**, by `CREATE TABLE … PARTITION OF` or by `ALTER TABLE … ATTACH PARTITION` (the row-level `UPDATE`/`DELETE` trigger of this mechanism *is* cloned by both). Both guards are enabled **`ALWAYS`** (`tgenabled = 'A'`), because `session_replication_role = 'replica'` suppresses an `'O'` trigger with its `tgenabled` unchanged. And what is asserted of them is that they **refuse** — the forbidden statement executed as the owner inside a rolled-back transaction, expecting `42501` — never that they exist: a guard's body can be replaced by `CREATE OR REPLACE FUNCTION` without touching any trigger, and every presence check in this ADR reports green over it (executed; Amendment 2). `aurora_app` never holds `TRUNCATE` on the parent or on any partition — that is mechanism 1, and its ACL assertion is what keeps it true. What none of this reaches is a role that can execute DDL; that is stated below and in Amendment 2 rather than claimed as covered.

**What none of the three prevents, and what detects it.** A role that can execute DDL on the table can `ALTER TABLE … DISABLE TRIGGER`, `DROP TRIGGER`, drop a partition or drop the table. That role is `aurora_migrator`, reachable only through the DDL path of ADR-0027 and never from a request — `aurora_app` has no DDL. Against a DDL-capable role the control was described as **detection, not prevention** — the hash chain of §5 — and **that is false as written, because the chain is unkeyed.** `hash = SHA256(prev_hash ‖ canonical(row))` uses a published algorithm over a pinned canonical form, so the same role can recompute it. Executed: dropping a middle partition gives `BROKEN at seq 7`, and one `UPDATE` loop recomputing the suffix returns it to `VERIFIES CLEAN` with six rows. What the chain detects is therefore **accidental loss, storage corruption and an actor who does not recompute** — not the role this paragraph names. Amendment 2 states this and what follows from it; the keyed-chain question is routed, not answered there. `VerifyAsync` reports the first broken link. Two cases are added to the tamper test of the writer row (**B-16.2** in `../BACKLOG.md`'s split of this ADR's work — schema and enforcement, then writer and chain): disable the trigger as the owner, edit a row, re-enable, verify — and drop a partition, verify.

**The chain alone does not catch removal at either end — the tail or the prefix — and against a role that can write it catches nothing at all, because it is unkeyed (Amendment 2).** Deleting the most recent rows leaves a chain that is internally consistent; so does deleting the oldest, because nothing re-checks that the surviving first row is the tenant's first row; and a middle removal, which does break a link, is repaired by one `UPDATE` loop. **The emptied trail is the degenerate case of both: a chain of zero rows verifies clean, and so does a chain that restarts from a first row whose `prev_hash` is the 32 zero bytes of §5.** Amendment 2 carries the executed results and the reason the obvious repair — anchoring the first row — is not available. The mechanism for that is ADR-0018's daily job writing the chain head to `catalog.operator_audit_event`, which is **not built and not scheduled** — it needs the row that creates that table (`../architecture/solution-layout.md` §6.4 item 5) and a scheduler for platform jobs (`../BACKLOG.md` `FOLLOWUP-031`, which ships `Aurora.Platform.Jobs`). Until both exist, tail truncation by a DDL-capable role is **undetected**. This is a limitation of the system as it will be after both audit rows land, stated here rather than described as covered; Amendment 2 is what removes the case that needed no DDL at all.

**The catalog's own append-only tables.** `catalog.operator_audit_event` and `catalog.erasure_replay_log` **do not exist**. No task had created them, B-05 did not, and this ADR does not create them — `../architecture/solution-layout.md` **§6.4 item 5** is the row that does, and until it is transcribed and built the two tables are still absent. That migration: grants `aurora_app` exactly `SELECT, INSERT`; records that decision in `CatalogSchemaAllowlist.AppRolePrivileges` **with the writer named**; attaches the mechanism-3 trigger; and asserts `pg_default_acl` holds **no** row for schema `catalog`, because mechanism 2 must not be copied there. What B-05 did do is delete the blanket `ALTER DEFAULT PRIVILEGES … GRANT` that would otherwise have handed those tables `UPDATE` and `DELETE` on creation.

Mechanism 2 is **not** applied to the `catalog` schema and must not be: `catalog.tenant` and its neighbours legitimately need `UPDATE`, so a schema-wide default of `SELECT, INSERT` would be wrong there and would have to be overridden table by table — the per-table memory this ADR exists to remove. That asymmetry is precisely why the audit table lives in its own schema, in a tenant database and in the catalog alike.

### 3. Partitioned from day one

`audit.audit_event` is RANGE-partitioned monthly on `occurred_at`, with the next two months pre-created by a platform job and a `DEFAULT` partition that a health check asserts is empty. Every primary key and unique constraint includes `occurred_at`, because PostgreSQL requires the partition key in them — which is precisely why this cannot be retrofitted cheaply later. ADR-0018 already names monthly partitioning as the mitigation for audit volume; converting the largest table in a tenant database to a partitioned one, across every tenant, under lock, is not a migration we are willing to owe ourselves. The chain order is `(occurred_at, sequence)`.

### 4. The write path

`IAuditWriter` in `Aurora.Platform.Audit.Contracts`:

```
Task WriteAsync(TenantAccess access, DbContext transaction, AuditEvent e, CancellationToken ct);
```

- **`TenantAccess`, not `TenantScope`** (ADR-0027 §1), so the same writer serves a request, a job and the provisioning saga's own step 8 — which must write a tenant-side event before any user has ever signed in to that tenant.
- **The caller's `DbContext` is a required parameter.** ADR-0018 requires the audit row to be written in the same transaction as the change it records; passing the transaction owner makes that structural instead of a convention a reviewer has to catch. Two tests: a rolled-back business transaction leaves zero audit rows, and a forced audit-write failure rolls back the business change.
- **The actor is an explicit parameter**, `AuditActor(ActorType, ActorId?, Display)` — never read from ambient state. Provisioning's actor is the operator who requested it; there is no signed-in user, and an audit writer that can only describe a signed-in user cannot record provisioning, package installs or jobs.

### 5. The hash chain is specified, not left to the implementer

`hash = SHA256(prev_hash || canonical(row))`, `prev_hash` of a tenant's first row = 32 zero bytes. `canonical` is pinned in the ADR-level sense: a fixed, ordered field list; UTF-8; instants as RFC 3339 UTC with microsecond precision; decimals in invariant format with no trailing-zero normalisation; a single documented null sentinel. An unpinned canonical form is a chain that breaks on a framework upgrade and cannot be told apart from tampering.

Writes serialise per tenant with `pg_advisory_xact_lock(hashtext('aurora.audit'))` — per tenant database, so it is not a fleet-wide serialisation point. `VerifyAsync(range)` returns the first broken link. Its test writes N events, verifies, then **tampers with a row as the owner role and asserts verification fails**. A chain verifier that has never been shown failing is not evidence of anything.

**And a tamper test that never recomputes is not evidence either.** Every tamper case specified in this ADR and in `../architecture/solution-layout.md` is of the **non-recomputing** form, so the suite can pass forever while the attack it exists for succeeds. Executed: drop a middle partition → `BROKEN at seq 7`; run one `UPDATE` loop recomputing `prev_hash` and `hash` over the surviving suffix → `VERIFIES CLEAN`, on both the link-only and the anchored verifier, six rows. The chain is unkeyed `SHA256` over a canonical form this ADR publishes, so recomputation needs nothing the attacker does not already have. **A third case is therefore required: tamper, recompute, and assert `VerifyAsync` returns clean** — a test that pins the limitation rather than a guarantee.

**And the mechanism that makes it fire has to be stated, because the natural implementation has none.** A recompute written the obvious way calls the production hashing code, so on the day the chain becomes keyed the recompute becomes keyed with it, the tampered chain still verifies, and the case stays green forever — a tripwire that cannot fire, which is the defect this amendment exists to remove. The recompute is therefore **implemented in the test from §5's published construction — SHA-256 over the canonical field list — sharing no code with the writer**, which is also the only honest model of the attacker, who has the ADR and not our types. The firing mechanism is one assertion in front of the tamper: **the independently computed hash of every untampered row equals its stored hash**, reported with the row count. Executed: unkeyed, `published construction reproduces every stored hash (rows checked: 5)`; with the writer changed to prepend a key and nothing else touched, `TRIPWIRE FIRED at seq 6: the published construction no longer reproduces stored hashes (rows checked: 6)`. It fires on keying, on a canonical-form change and on an algorithm change alike, and its count stops it passing over an empty table.

### 6. Two sides of the tenant boundary, neither substituting for the other

SPEC-001 BR-7/AC-6: the tenant-side event goes to `audit.audit_event` in the new tenant database; the platform-side event goes to `catalog.operator_audit_event`. Provisioning attempts and failures are platform-side only, because the tenant database may not exist yet.

### 7. What is deferred, explicitly

The `[Auditable]` `SaveChangesInterceptor` (ADR-0018 §2) and the fitness rule banning `ExecuteUpdate`/`ExecuteDelete` on `[Auditable]` entities are a **second** piece of work. They are needed before the first business module writes data (B-15.1), not before provisioning can write one explicit event. Retention (`platform.retention_rule`), legal hold and subject erasure remain ADR-0018's, unscheduled here and not part of the walking skeleton.

## Consequences

- Positive: the walking skeleton can demonstrate the property the product is sold on, and SPEC-001 AC-6 becomes testable instead of aspirational.
- Positive (**restated by Amendment 1**): the schema-level **default grant** of `SELECT, INSERT` means the next table created in `audit` by the DDL-path role is append-only to `aurora_app` by where it is created, not by whether its author remembered ADR-0004 rule 5 — and a test that creates a table after the migration and probes it fails if the default-ACL row is missing. The original wording of this bullet rested on `ALTER DEFAULT PRIVILEGES … REVOKE`, which is a no-op; see Amendment 1.
- Positive: `TenantAccess` in the writer's signature means provisioning, jobs and requests share one audit path and one set of tests.
- Negative: one more schema and one more migration set per tenant database, in the migration order of ADR-0007 §7.1 (`platform` → `audit` → module schemas → `pkg_*`).
- Negative: partitioning and the hash chain are more machinery than the walking skeleton strictly needs. Both are here because both are expensive to add after the table has rows in every tenant.
- Negative: a serialisation point per tenant on audit writes. ADR-0018 already names this and its fallback (chain per day rather than per event); measure before changing.

## Revisit when

Audit volume forces partitions out of the tenant database into an archive store; a regulator requires read auditing; or the per-tenant chain lock shows up in a latency profile, at which point ADR-0018's per-day chaining is the prepared answer.

## Amendment 1 (2026-09-11) — §2's second mechanism did nothing, and its closing sentence described work that had not happened

**Raised by** `../reviews/security-B-05.md` finding H-3, which executed the statement rather than reading it. **Amended by** the architect. The decision of this ADR — `audit.audit_event` in its own schema in the tenant database, monthly partitioning, `IAuditWriter` taking `TenantAccess` and the caller's `DbContext`, the pinned hash chain — is **unchanged**. What changes is how §2 says append-only is enforced, which was wrong in two ways.

### What §2 used to say

> ### 2. Append-only, enforced three ways, each tested as the runtime role
>
> 1. `REVOKE UPDATE, DELETE ON ALL TABLES IN SCHEMA audit FROM aurora_app`;
> 2. `ALTER DEFAULT PRIVILEGES FOR ROLE aurora_migrator IN SCHEMA audit REVOKE UPDATE, DELETE ON TABLES FROM aurora_app` — so a table added to `audit` later inherits the policy;
> 3. a `BEFORE UPDATE OR DELETE` trigger that raises, which also catches `aurora_migrator` (the owner, whom privileges do not restrain).
>
> **The tests connect as `aurora_app` and as `aurora_migrator` and assert the statement fails.** A test that runs as the fixture's superuser, or that asserts the `REVOKE` statement was executed rather than probing `has_table_privilege` and running the `DELETE`, is the test that passed on B-05 while the table was deletable. The same three-way enforcement is retrofitted to `catalog.operator_audit_event` and `catalog.erasure_replay_log` (B-05 M-1's fix).

### What was wrong with it

1. **Mechanism 2 is a no-op.** `ALTER DEFAULT PRIVILEGES … REVOKE` on a privilege the role never had by default creates no `pg_default_acl` row and changes nothing, now or ever. Verified on PostgreSQL 17.11: `0 rows`, and a subsequent explicit `GRANT … UPDATE, DELETE` on a new `audit` table succeeded. It was the stated reason for choosing the `audit` schema over `platform`, so the Options table and the Consequences bullet that rested on it were wrong too. This is the B-05 M-1 failure mode — a `REVOKE` whose effect was never asserted — pre-installed in the ADR written to avoid it.
2. **The acceptance criterion it generated could not fail.** "Create a table in the schema afterwards and re-probe that `UPDATE` is refused" passes against the no-op, because a new table grants `aurora_app` nothing at all. The corrected criterion asserts the **exact** privilege set, which fails in both directions.
3. **The closing sentence described work nobody had done.** `catalog.operator_audit_event` and `catalog.erasure_replay_log` do not exist; B-05 did not retrofit anything to them. A reader six months from now would have believed two tables were protected by a trigger and two revokes when they are protected by nothing, because they are not there.
4. **`has_table_privilege` was named as the probe.** `../reviews/security-B-05.md` H-1 then showed it blind to a column-level grant and short by one privilege on PostgreSQL 17 (`MAINTAIN`). The replacement §2 compares the ACL.

### What changed as a result

- §2 is replaced in full (above), naming three mechanisms that were each executed, plus what none of them prevents and what detects that instead.
- The Options-table cell for the chosen option and the corresponding Consequences bullet are restated in place, with the superseded wording struck through.
- `../architecture/solution-layout.md` §6.4 re-specifies **B-16.1**'s acceptance criteria, and §6.1's B-16.1 row is marked as overridden. The project-manager must transcribe the new criteria into `../BACKLOG.md`'s B-16.1 row, which still quotes the no-op statement and the criterion that cannot fail.
- Withdrawing the retrofit sentence left two ADR-0007 tables and the tail-truncation follow-up depending on a row nobody owned. `../architecture/solution-layout.md` **§6.4 item 5** creates `catalog.operator_audit_event` and `catalog.erasure_replay_log` with the grants, the trigger and the zero-row `pg_default_acl` assertion; the follow-up depends on it by name. SPEC-001 BR-7 already has B-07.1 and B-07.4 writing to a table nothing created.
- The event-trigger option (`ddl_command_end`, which would attach the guard trigger to any new table in `audit` automatically) was considered and **rejected**: `CREATE EVENT TRIGGER` requires superuser on PostgreSQL 17.11 — verified, `ERROR: permission denied to create event trigger … HINT: Must be superuser` — and ADR-0004 rule 2 defines no superuser role (`aurora_admin` has `CREATEDB`; `aurora_migrator` owns schemas). Adopting it would mean requiring superuser in every environment, which is a larger and less portable commitment than the property is worth. The positive default grant reaches the same "protected by where it is created" property for the privilege half, and the trigger half stays explicit per table.

## Amendment 2 (2026-09-12) — the truncate guard reached only partitions a job creates, and no such job exists

**Raised by** the third security review of ADR-0029 (PR #5) finding M-1, which **executed** `TRUNCATE catalog.authentication_event_default` as the owner and emptied the trail while the parent's guard was in place; carried in `../BACKLOG.md` as `FOLLOWUP-026`. **Amended by** the architect, with every statement below executed against `postgres:17-alpine` — **PostgreSQL 17.11**, the pinned image — on 2026-09-12, as `aurora_migrator` (the schema owner) and as `aurora_app` (the request-path role). The decision of this ADR — `audit.audit_event` in its own schema in the tenant database, monthly partitioning, `IAuditWriter` taking `TenantAccess` and the caller's `DbContext`, the pinned hash chain — is **unchanged**. What changes is §2 mechanism 3.

**The findings of five security reviews of this amendment (PR #9) are incorporated below**, review by review, each executed by the reviewer and re-executed here. From the first review: the guard's **body** can be replaced by `CREATE OR REPLACE FUNCTION` without touching any trigger, which the first draft's presence-based invariant could not see (HIGH-1); `DETACH PARTITION` **deletes cloned triggers**, so detach → delete → re-attach left the invariant printing its own green output with a row gone (HIGH-2); and `session_replication_role = 'replica'` suppresses an `'O'` trigger with `tgenabled` unchanged (MEDIUM-1). That draft had replaced a rule that checked the wrong thing with a rule that checked **presence** rather than **effect**.

From the second review: the repair itself was **not implementable as written** — a clone owns the parent's trigger name and cannot be dropped, and the fallback an implementer is forced into reopens the detach hole with every published number unchanged (HIGH-1); the residual's statement about what the hash chain detects was **wrong at the prefix**, which is the end retention removes, and the cover named for it does not see prefix removal either (HIGH-2); `RETURN NULL` is not the destructive body for a *row* guard (MEDIUM-1); and a session-keyed guard body is a permanent weakening that both probes report green over, falsifying this amendment's own claim that permanent weakenings are visible (MEDIUM-2).

From the third review: the body fingerprint **pinned a function by name and nothing bound that name to a trigger**, so moving the weakening into the trigger's `WHEN` clause or re-pointing the trigger at a look-alike function left all three checks green and the trail one `SET` from empty (HIGH-1); "the chain detects the middle" is **false against a role that can write**, because an unkeyed chain is recomputable in one `UPDATE` loop, and every tamper case specified anywhere is of the non-recomputing form (HIGH-2); and the clause, corrected here, was **reopened 113 lines above it** in `solution-layout.md` §6.2's `B-18.9` row — the row that creates the very table the original attack emptied — where it had been flagged and left three times (HIGH-3).

From the fourth review: `tgtype` — `CREATE OR REPLACE TRIGGER … BEFORE UPDATE` drops `DELETE` from a guard (`27` → `19`) while it stays partition-local, `'A'`, unconditioned and calling the shipped body, and every check was byte-identical while `DETACH` → `DELETE 2` → `ATTACH` took the trail from three rows to one. And the third review's fix was **half wrong**: "the binding check is the only witness" was false against the check as specified, because its population was `tgparentid = 0` on leaves, which left the parent's trigger and every clone outside it.

From the fifth review, which attacked the whole-row shape and could not beat it on its own terms — it reproduced all four previous blockers and both new columns under the one mechanism — but beat the **clause**: part 3 specified the **live** side of the comparison and left the **pinned** side unconstrained, so a name-keyed comparator that skips a column the pin does not carry reads a missing pin as agreement and reproduces round 3's blocker exactly (`triggers: 8, column comparisons: 120, findings: 0` with the trail one `SET` from empty) — HIGH-1, and the fourth form this branch has hit, **a correction that re-introduces what it fixed**. The variance list and the self-incompleteness guard were scoped to `pg_trigger` while part 3 mandates the whole `pg_proc` row, and `pg_proc` has **nine** oid-valued columns with no resolver, so the check as written **refuses to run on a correct system** and the `pg_proc` half — `prosrc`, `prosecdef`, `proconfig` — had no completeness guard at all (HIGH-2: *"five names is fourteen"*). And `column comparisons: 368` was unreachable by any correct implementation: nineteen `pg_trigger` columns minus three variance is sixteen, not seventeen, so the number is **360** (MEDIUM-1), and resolving an oid through a bare `::regprocedure` or `::regclass` cast makes the comparison depend on `search_path` (LOW-1). All four are executed and re-executed here on PostgreSQL 17.11.

**The fourth reviewer's own summary is the one that changed this amendment's shape: four blockers, each a `pg_trigger` column nothing was reading** — the body, `tgparentid`, `tgqual` and `tgfoid`, `tgtype`. Four rounds each added a predicate and the next round found the next unread column; `pg_trigger` has **19** columns and the predicates read six. That is not convergence, it is a list chasing a surface. **Part 3 is therefore no longer a list of predicates but a whole-row comparison against what the migration created**, with a short, auditable statement of what is *not* compared. A column PostgreSQL adds next is then a **difference**, not a gap nobody thought of.

The thread running through all of it: **a mechanism named in a document is not a mechanism until someone executes it**, and every repair on this branch was carried by something unverified until a reviewer ran it. The narrower lesson, which the shape change is the answer to: **a check that enumerates what it looks at is bounded by the imagination of whoever wrote the list.** Compare everything and name the exceptions instead.

### What §2 mechanism 3 used to say

> - *Plus* a `BEFORE TRUNCATE … FOR EACH STATEMENT` trigger, **with a verified limitation: truncate triggers are not cloned to partitions.** `TRUNCATE audit.audit_event` was refused; `TRUNCATE audit.audit_event_2026_09` succeeded and emptied the table. Therefore the job that pre-creates partitions (§3) attaches the truncate trigger to each partition it creates, and its test truncates a **job-created** partition as the owner and expects `42501`. `aurora_app` never holds `TRUNCATE` — that is mechanism 1, and its ACL assertion is what keeps it true.

### What was wrong with it

1. **It hangs the guarantee on a job that does not exist.** `Aurora.Platform.Jobs` is in no bootstrap row; the partition pre-creation job of §3 is `FOLLOWUP-031`, named in three documents before it had an id. A mechanism whose only carrier is unbuilt work protects nothing today, and Amendment 1 withdrew a sentence for exactly this shape — describing work nobody had done.
2. **The `DEFAULT` partition is not job-created and never will be.** The migration creates it (§3). So even on the day the job ships, the rule as written does not reach the partition the reviewer actually truncated — and the `DEFAULT` partition is where every row lands whenever no month partition covers `occurred_at`, which without the job is every row after the pre-created months run out.
3. **Nothing detects the result.** §2 already records that the hash chain does not detect truncation of the tail, and an emptied table is the degenerate tail truncation: zero rows verify clean, and a trail that restarts from a first row with the 32 zero bytes of §5 verifies clean too. So the two halves compose into the finding: **a tenant's financial audit trail can be emptied and then pass `VerifyAsync`.**
4. **The cost of the attack was one statement.** Not a `DROP TRIGGER`, not a `DISABLE TRIGGER`, not a partition drop — a plain `TRUNCATE` naming a partition, available to the schema owner with no other DDL. It sat below the threshold the ADR had declared its detection-not-prevention boundary.

Executed, reproducing it on `audit.audit_event` with three rows and the guard on the parent only:

| Statement, as `aurora_migrator` | Result | Rows left in the parent |
|---|---|---|
| `TRUNCATE audit.audit_event` | `42501` | 3 |
| `TRUNCATE audit.audit_event_default` | `TRUNCATE TABLE` | 1 |
| `TRUNCATE audit.audit_event_2026_09` | `TRUNCATE TABLE` | **0** |

`pg_trigger` after the migration shows why: the row-level guard (`tgtype` 27 = `ROW` 1 + `BEFORE` 2 + `DELETE` 8 + `UPDATE` 16) is present on the parent **and both partitions**; the truncate guard (`tgtype` 34 = `BEFORE` 2 + `TRUNCATE` 32, statement-level) is present **on the parent only**. `ALTER TABLE … ATTACH PARTITION` behaves the same way: the attached partition came out carrying the row-level guard and no truncate guard.

### The decision — one clause, for every append-only partitioned table this system has

**Every partition of an append-only partitioned table carries its own guards — the `BEFORE TRUNCATE … FOR EACH STATEMENT` guard and the `BEFORE UPDATE OR DELETE … FOR EACH ROW` guard, the `DEFAULT` partition included — created on the partition itself by the same migration step that creates or attaches it, enabled `ALWAYS`; and what is asserted is that they *refuse*, never that they exist.**

It is one clause because it is written here, about the shape rather than about a table: it binds `audit.audit_event` in every tenant database and `catalog.authentication_event` in the catalog (ADR-0029 A2.1 partitions it monthly with a `DEFAULT` partition) and anything partitioned that is added to either later. `../architecture/solution-layout.md` §6.4 item 1 criterion 5 is the row form for the first, and §6.4 item 5 carries it for the catalog.

1. **Creation — one helper, one migration step, and the partition-local guards carry their own names.** The helper issues the `CREATE TABLE … PARTITION OF` or `ALTER TABLE … ATTACH PARTITION`, then `CREATE TRIGGER` for **both** guards **on the partition itself under a distinct name — the parent guard's name plus `_local`** — then `ALTER TABLE … ENABLE ALWAYS TRIGGER` for each: one step, one transaction. The migration creates the `DEFAULT` partition and the initial month partitions through it, so the guards exist before any job does, and `FOLLOWUP-031`'s partition job calls the same helper rather than carrying its own copy of the rule.

   **Why a distinct name, and why this is not cosmetic.** The first draft of this clause said "created on the partition, never by clone" and was **not implementable as written**: a partition's cloned row trigger owns the parent's trigger name, in both orders and irreversibly. Executed:

   | Attempt, as `aurora_migrator` | Result |
   |---|---|
   | `CREATE TRIGGER g_row … ON <partition>` after `CREATE TABLE … PARTITION OF` | `ERROR: trigger "g_row" for relation "ev_09" already exists` |
   | `DROP TRIGGER g_row ON <partition>` | `ERROR: cannot drop trigger g_row on table a.ev_09 because trigger g_row on table a.ev requires it` |
   | `CREATE TRIGGER g_row` on a standalone table, then `ATTACH PARTITION` | `ERROR: trigger "g_row" for relation "ev_10" already exists` |
   | The same three with the name `g_row_local` | all succeed; the partition ends up carrying **both** the clone and the local guard |

   An implementer who hits that error and falls back to the clone produces a system in which **every published number is unchanged and the trail still bleeds**. Executed on that exact fallback shape: the locator printed `leaf_partitions 2 / guarded_leaves 2 / guarded_parents 1`, the effect probe printed `probed: 4, refused with 42501: 4, silent: (none)` — and then `DETACH` left only the partition-local *truncate* guard on the detached table, `DELETE` returned `DELETE 2`, `ATTACH` restored the clone, and the trail went from 3 rows to 1 with both probes still printing the same numbers. The naming rule is what makes the clause executable; the next point is what makes it checkable.

   **`tgparentid = 0` is the mechanism, and nothing checked it.** A clone and a partition-local guard are indistinguishable in `tgname`, `tgtype` and `tgenabled`; they differ in `tgparentid`, which is `0` for a locally created trigger and the parent trigger's oid for a clone. Executed on the fallback shape: the published predicate counts **1** per leaf, and the same predicate `AND tgparentid = 0` counts **0**. Every criterion that asserts a partition-local guard carries `AND t.tgparentid = 0`. Without it, "created on the partition rather than cloned" is a convention with no mechanism — the class of defect this amendment exists to remove.

   **The parent keeps its row guard** even though the invariant does not count it: it clones, so a partition created by some path that bypasses the helper is not left completely unguarded. It is defence in depth, not the guarantee, and the `DETACH` result above is why it cannot be the guarantee.

   Two more executed facts that shaped this part: a truncate guard is **never** cloned to a partition, so it has no name to collide with and takes the `_local` suffix only for uniformity — one naming rule and one predicate covering both guards; and `CREATE TRIGGER` always produces `tgenabled = 'O'` (there is no `CREATE TRIGGER … ALWAYS`), while `ENABLE ALWAYS` on the parent reaches **cloned** triggers only — a partition's own truncate guard stayed `'O'` while the parent's went `'A'`. So the helper issues `ENABLE ALWAYS` per partition.

2. **The property is refusal, and the effect probe is the assertion.** Inside a transaction that is **rolled back**, execute the forbidden statement against **every** relation in `pg_partition_tree('<parent>')` — `TRUNCATE`, and `UPDATE`/`DELETE` against a seeded row — **connected as `aurora_migrator`**, and require SQLSTATE `42501` from each. The probe reports how many relations refused and **names any that were silent**.
   - *The `UPDATE`/`DELETE` half must seed its own row, inside the same rolled-back transaction.* A `BEFORE … FOR EACH ROW` trigger does not fire when no row matches: executed, `DELETE` on an **empty but correctly guarded** partition returns `DELETE 0` with no exception, and an unseeded probe reported `probed: 2, refused: 0, silent: h.ev_09, h.ev_default` over two perfectly good guards. That is a false **red** — which is worse than it sounds, because the repair an implementer reaches for is to accept "no exception and zero rows" as a pass, and that acceptance can never fail. Seeded: `probed: 2, refused: 2, silent: (none)`, with the rollback leaving nothing behind (`rows_after 0`). Every partition is probed, including empty ones and the `DEFAULT` partition, whose seed needs an `occurred_at` no month partition covers. **All seeding happens before any statement is attempted**, not interleaved with the loop: a first draft of this probe seeded each leaf as it reached it and reported `silent: w.ev:delete` on a correct system, because the parent was probed before any leaf had a row. Executed, and the ordering is part of the specification for that reason.
   - *Why rolled back.* The run that discovers a broken guard is the run in which the forbidden statement **succeeds**. A probe that truncates for real destroys the trail it is checking, on exactly that run. Executed: against a guard whose body had been replaced, the probe went red **and the three rows were still there afterwards**; `TRUNCATE` is transactional in PostgreSQL, so this costs nothing but an `ACCESS EXCLUSIVE` lock for the length of the probe.
   - *Why as the owner, and why this is the one probe that does not connect as the runtime role.* Connected as `aurora_app`, `TRUNCATE` of a **completely unguarded** partition returns `42501: permission denied for table` — executed. That is the same SQLSTATE the guard raises, from the privilege check, with no trigger present at all: an effect probe run as `aurora_app` reports green over an unguarded table. As `aurora_migrator`, who holds `TRUNCATE` by part 5, the privilege path cannot produce `42501`, so a `42501` can only have come from the guard. Mechanism 1's rule — *every probe connects as the role it is testing* — still holds: this probe is testing the guard, and the guard's subject is the owner.

3. **The binding is asserted as a whole-row comparison, not a list of predicates — and both sides of the comparison are closed.** Pin, as literal expected values in the test, the **entire `pg_trigger` row** of every guard the migration creates and the **entire `pg_proc` row** of the function each one calls; compare the live catalog against that set, **column by column, every column**, as a set (so a missing guard, an unexpected guard and a changed guard are all differences). The comparison reports **how many triggers and how many column comparisons** it performed, each **read off the runtime enumeration** rather than written here as a literal and copied into the test.

   **All three parts of this clause are migration-time assertions, not runtime health checks.** They run as `aurora_migrator` in the integration test that follows a migration of a freshly created database; they are on no request path; and none of them belongs in the per-tenant health-check family of ADR-0007 §9.4 — promoting one there would need a standing DDL-role credential in the runtime and an `ACCESS EXCLUSIVE` lock on every audit partition, which is the opposite of what ADR-0027 arranges. Whether a live system needs an equivalent is `FOLLOWUP-033`'s question, and this clause does not answer it.

   **This replaces four rounds of predicates, and that is the point.** Each of the first four security reviews of this amendment found the same defect in a different column: the guard's **body** (round 1), `tgparentid` (round 2), `tgqual` and `tgfoid` (round 3), `tgtype` (round 4 — `CREATE OR REPLACE TRIGGER … BEFORE UPDATE` takes a guard from `27` to `19`, dropping `DELETE`, while it stays partition-local, `'A'`, unconditioned and calling the shipped body). A fifth list would have been beaten by a sixth column: `pg_trigger` has **19** columns in PostgreSQL 17.11 and the predicates read six of them. Executed, the whole-row comparison catches all four rounds and two more nobody had reached — `tgattr` (`BEFORE UPDATE OF <column>` → executed on the §3 shape, `tgattr is '3', pinned ''`, the door the `B-19` author found from the other side) and `proconfig` (`ALTER FUNCTION … SET search_path`) — under one mechanism, with no predicate written for any of them.

   - *The comparison is over the **union** of the two sides, on both axes — and this is the link four rounds of this clause did not read.* The live side is enumerated from `pg_attribute` at runtime; the pinned side is a literal written by hand. **"Compare every column" says nothing about what happens when one side does not carry a column the other does, and a comparator that skips on a lookup miss reads a missing pin as agreement.** The fifth review executed exactly that against this shape: a name-keyed comparator, a `WHEN` clause put on the parent's `g_row` (clones follow) and on `ev_09.g_row_local` with `ENABLE ALWAYS` re-issued so `tgqual` was the only differing column, `triggers: 8, column comparisons: 120, findings: 0`, effect probe green — and then `SET aurora.maint = 'on'; DELETE FROM a.ev_09;` left zero rows. That is round 3's blocker reproduced against the new shape by the shape's own under-specification. So the comparison is defined on both axes:
     - **Row axis.** The key is the pair (`tgrelid` rendered as `schema.relation`, `tgname`) — schema-qualified for the same reason the resolvers are, and that is why those two columns are in the variance list rather than compared. The compared keys are the union of the live keys and the pinned keys. A key pinned and not live is `MISSING`; a key live and not pinned is `UNEXPECTED`. Both are findings, and neither contributes column comparisons — there is nothing on the other side to compare against.
     - **Column axis.** For a key present on **both** sides, the compared column names are the union of the names the runtime enumeration returned and the names the pin carries. A live column with **no pinned value** is a finding — `<relation>.<trigger>.<column> NO PINNED VALUE` — reported and counted exactly like a differing value. A pinned column the enumeration does **not** return is a finding — `PINNED BUT NOT IN CATALOG`, which is what a pin written against an older PostgreSQL looks like. **No branch of the comparator may `continue` on a lookup miss**, and a test asserts that: pin one column short and the run must report a finding per affected key, not a smaller count.
     - A short pin therefore surfaces as **findings**, not merely as a short count, and the count stays reproducible, since the union equals the live column set whenever the pin is a subset of it.
   - *The variance list, which is the whole of what is not compared, stated **per catalog**.* In `pg_trigger`: `oid`, the row's own identity, and `tgrelid` and `tgname`, the comparison key — **three of nineteen, leaving sixteen**. In `pg_proc`: `oid` alone — **one of thirty, leaving twenty-nine**. Nothing else is excluded from either catalog. Nineteen and thirty are `select count(*) from pg_attribute where attrelid = '<catalog>'::regclass and attnum > 0 and not attisdropped` on PostgreSQL 17.11, executed; the check reads them from that query at runtime and prints them, so this sentence is a record of what it printed and not the source the test copies from.
   - *Every **oid-valued** column of **either** catalog is compared by its **resolved name**, because an oid is assigned at creation and means nothing across databases.* Oid-valued is decided from `pg_attribute.atttypid` at runtime — type `oid`, `oidvector`, `oid[]`, or any `reg*` alias type — **over the compared columns, so the variance list is applied first.** That ordering is load-bearing: the raw enumeration returns **seven** oid-typed columns in `pg_trigger` and **ten** in `pg_proc`, because `oid`, `tgrelid` and `pg_proc.oid` are themselves oid-typed, and an implementer who classifies before excluding meets three columns with no resolver and **refuses to run on a correct system** — HIGH-2's failure mode reached from the other side. After the variance list, on 17.11, it is **five columns in `pg_trigger` and nine in `pg_proc`: fourteen resolvers, not five.** An earlier draft of this clause named only the `pg_trigger` five while mandating the whole `pg_proc` row, which made the check **refuse to run on a correct system** (the fifth review implemented it and got nine unresolved `pg_proc` columns) and left the `pg_proc` half — the half carrying `prosrc`, `prosecdef` and `proconfig` — with no completeness guard at all. The fourteen:
     - **`pg_trigger` (five).** `tgfoid` → the function identity, schema-qualified. `tgparentid` → the parent trigger as `schema.relation.trigger`, or `none` at `0`. `tgconstrrelid`, `tgconstrindid` → `schema.relation`, or `none` at `0`. `tgconstraint` → `schema.constraint`, or `none` at `0`.
     - **`pg_proc` (nine).** `pronamespace` → the schema name. `proowner` → the role name, via `pg_get_userbyid`. `prolang` → `pg_language.lanname`. `provariadic` → a schema-qualified type name, or `none` at `0`. `prosupport` (`regproc`) → a schema-qualified function identity, or `none` at `0`. `prorettype` → a schema-qualified type name. `proargtypes` (`oidvector`) → the ordered list of schema-qualified type names. `proallargtypes`, `protrftypes` (`oid[]`) → the same, or `none` when null.
     - **Every resolver is schema-qualified by construction, never a bare `::regclass`, `::regprocedure` or `::regtype` cast to text.** Those casts suppress the schema whenever `search_path` would find the object, so one correct database renders `tgfoid` as `refuse()` in one session and `a.refuse()` in another, and `tgrelid`/`tgparentid` as `ev_09` or `a.ev_09` — both executed on 17.11. A literal pin written in one session and compared in another then goes red on a correct system, and the repair an author reaches for on a false red is to weaken the resolver, which is how columns leave the compared set. Build the name from `pg_namespace` explicitly — `format('%s.%s(%s)', pronamespace::regnamespace, proname, pg_get_function_identity_arguments(oid))` and its `pg_class` and `pg_type` equivalents — **and** run the pin-generating session and the comparing session with `search_path = pg_catalog`, so that a resolver someone writes as a cast anyway is at least deterministic.
   - *Why default-compare is the load-bearing choice.* A new PostgreSQL column is compared **automatically**, so it shows up as a difference the first time it differs — it cannot be a gap nobody thought of. The one thing that could still slip is a new **oid-valued** column, which needs a resolver; so the check enumerates **each** catalog's columns at runtime and **refuses to run** when it meets one it cannot resolve, **naming the catalog it found it in**: `UNRESOLVED oid-valued column(s) in pg_proc: proallargtypes — classify them before this check can claim completeness`. Executed, with one resolver removed to stand in for a column PostgreSQL adds next. A completeness claim that cannot detect its own incompleteness is the defect this whole amendment is about — and a completeness claim scoped to **one** of the two catalogs it compares is that same defect wearing the other catalog's name, which is precisely how fourteen resolvers were published as five.
   - *The population is every non-internal trigger on every relation in `pg_partition_tree`, parent included — not the leaf-local ones.* The predicate form scoped itself to `tgparentid = 0` on leaves, which put the parent's trigger and every clone **outside** what it examined: re-pointing the parent at a permissive look-alike left `triggers examined: 7` and no finding, and the third review's "the binding check is the only witness" was false for exactly that reason. Under the whole-row comparison the same act turns **three trigger rows** red — `ev.g_row`, `ev_09.g_row`, `ev_default.g_row` — each carrying `tgfoid is 'a.lookalike()', pinned 'a.refuse()'` among its differences. `findings:` counts **differences, not rows**, so the run prints `triggers: 8, column comparisons: 360, findings: 9`: the look-alike also differs in `proname` and `prosrc`, because the whole `pg_proc` row is compared. Executed both ways.
   - *Counts, derived rather than restated.* `triggers:` is the number of live rows the population query returned. `column comparisons:` is the sum, over the keys present on **both** sides, of the size of that key's column union. On the shape in §3 that is 8 guards × (16 compared `pg_trigger` columns + 29 compared `pg_proc` columns) = **360**, and the run prints the arity it captured — `captured: trigger columns 16, function columns 29` — so that the day PostgreSQL adds a column the number moves on its own and nothing has to be told. **This figure was published as `368` through four revisions of this clause and no correct implementation produces it:** it read the variance list as removing two `pg_trigger` columns rather than three. That is `CLAUDE.md` self-check #1, and it was worse than bookkeeping — before the union rule above, a short pin showed as a short count and nothing else, so a wrong reference count destroyed the only signal separating *compared everything* from *compared what I pinned*. **A run reporting `triggers: 0` or `column comparisons: 0` has measured nothing and fails**, which is a different outcome from `findings: 0` over a non-zero count, and that is the pass.
     - *And the count is only as good as the transport under it.* `prosrc` contains newlines, so a reader that splits psql's output on lines silently fragments rows and then reports as though it had read all of them. Executed while writing this clause: the line-splitting version of the same implementation printed `triggers: 9, column comparisons: 331, findings: (none)` on the correct shape — a wrong population and a wrong count, both plausible-looking, and green. Carry catalog values in a structured transport (`json_agg`, or a client that returns typed rows), and assert that the population size equals the number of rows the population query reports.
   - *The chain from each assertion to the behaviour, and the link each one stops at.* Every break on this clause has lived on **a link nothing was reading**, so the chain is written out here rather than left to be inferred. The trail is safe from a statement **iff** every relation in `pg_partition_tree` refuses it ⟵ each relation carries a guard that fires for that event ⟵ the guard is enabled in this session's replication role, is not conditioned away by a `WHEN` clause, and covers the event ⟵ the function it points at raises. **Part 2 walks that chain to its end** for the statements it issues — and stops at *this session, now*: it cannot see a weakening conditioned on state it does not set. **Part 3 walks it to "every compared column of the trigger row and of the function row equals what the migration created"** — and stops one link short of *the body is correct*, because a migration that ships a wrong body pins the wrong body (executed by the fifth review: `findings: 0`). **Part 4 walks it to "the set of relations is the set the migration created"** — and stops at *existence*, saying nothing about any trigger. Three different stopping points on one chain: that is why all three are required, and it is what the fourteen-row matrix below measures rather than asserts.

4. **The relation population is a separate assertion, because the comparison above cannot see it.** The whole-row comparison keys on `(relation, trigger)`; a relation carrying **no** trigger contributes no row and is therefore invisible to it. So, separately: every leaf in `pg_partition_tree` is expected, **exactly one `DEFAULT` partition exists** and is empty, and the leaf count meets its floor. Executed: a partition added by hand surfaced only as `ev_10.g_row UNEXPECTED` — its inherited clone — and that is an accident of the parent having a row trigger, not a guarantee. The `DEFAULT`-existence half is not pedantry: dropping the `DEFAULT` partition re-enables `DETACH PARTITION CONCURRENTLY`, which parks a partition outside `pg_partition_tree` and so outside *every* check here.

   **Three questions, three mechanisms, and each covers the others' blind spot:** *does the guard refuse, now, for me?* — the effect probe of part 2, which is blind to anything conditional on state the probe does not create. *Is the guard the one the migration created, in every respect?* — the whole-row comparison, which is blind to a body that is wrong but unchanged. *Are the relations the ones the migration created?* — the population assertion, which is blind to everything about a guard except its existence. `B-19`'s author reached the same split from the other side and named it well: what the **probe** sees is what lets its own statements through; what the **binding** sees is what changes a guard's binding. The whole-row form is what makes the second one complete rather than merely current.

5. **`TRUNCATE` appears in no relation's ACL — parent or partition — for any role but the owner `aurora_migrator`.** That is mechanism 1's ACL comparison extended to partitions, and it is already true: executed, `aurora_app` truncating the parent gets `42501: permission denied for table`. Naming it here is the answer to "who may ever hold `TRUNCATE`": exactly one role, the DDL-path role of ADR-0027, and any other holder is a finding. It is also what makes part 2's probe discriminating — see the rejected `REVOKE` direction below.

6. **The parent keeps its own guards, and they are not what closes this hole.** Executed: with the parent's truncate guard dropped and every leaf guarded, `TRUNCATE <parent>` is still refused — a parent truncate fires each leaf's guard. The parent's guards stay because they are the only thing that refuses a truncate of a parent with **zero** partitions, which is the state a failed migration can leave behind.

**One executed fact both row forms depend on: a partition's ACL is not the parent's, and it differs by schema.** In `audit`, mechanism 2's schema-wide default grant reaches partitions too — a partition created by `aurora_migrator` came out `{aurora_migrator=arwdDxtm/aurora_migrator, aurora_app=ar/aurora_migrator}`, so `aurora_app` holds `SELECT, INSERT` on every partition. In a schema with **no** default privileges — `catalog`, by §2's closing paragraph and ADR-0029 A2.7 point 4 — the same `CREATE TABLE … PARTITION OF` leaves `relacl` **null**, and the partition is unreachable to `aurora_app` in every direction: a routed `INSERT` through the parent succeeds, because routing checks the **parent's** ACL, while a direct `INSERT`, `SELECT` or `TRUNCATE` on the partition returns `42501`. All executed. So a privilege comparison that carries `audit`'s expectation into `catalog` would accept a grant that makes a partition directly reachable and would never say so; `../architecture/solution-layout.md` §6.4 item 5 criterion 3 records the catalog's expectation — **empty** — in the place the allow-list is specified.

### What demonstrates each mechanism working, what makes it go red, and what leaves it green if the fix is wrong

### The limitation, written down instead of a claim

**A role that can execute DDL on the table can still empty it, and nothing this project has built detects that.** The acts, each executed: `DISABLE TRIGGER` then `TRUNCATE`; `DROP TRIGGER` then `TRUNCATE` or `DELETE`; `CREATE OR REPLACE FUNCTION` on the guard body — unconditionally, or keyed on a session setting so that both probes stay green; `DETACH PARTITION` then `DROP TABLE`; and `DETACH PARTITION`, `DROP TRIGGER`, `DELETE`, re-create, `ATTACH`. All are available to `aurora_migrator`, reachable only through the DDL path of ADR-0027 and never from a request.

Five things must be said plainly about that list rather than left to be inferred.

1. **The clause removes the case that needed no DDL at all, and leaves the cases that need DDL undetected.** Emptying the trail is no longer one `TRUNCATE` away. That is a smaller residual than the one the reviewer found, and it is the same boundary §2 already drew. It is not a new exposure; it is also not covered, and must not be written as if it were.

2. **The detach round trip is closed only by the naming rule and `tgparentid`.** `DETACH` deletes **cloned** triggers, so a row guard that exists only by clone is absent for the length of the detach. With the partition-local guard of part 1 the same `DELETE` is refused and the attacker must `DROP TRIGGER` first — but with the clone-fallback shape, which is what an implementer produces on hitting the name collision, `DETACH` → `DELETE 2` → `ATTACH` took a three-row trail to one **while the locator printed `leaf 2 / guarded 2 / parents 1` and the effect probe printed `probed 4 / refused 4 / silent (none)` throughout**. Executed. This is why `tgparentid` is compared rather than assumed: without it the residual's second line is false and nothing says so. It is now one of the sixteen compared `pg_trigger` columns of part 3, not a predicate someone had to think of.

3. **The hash chain detects nothing against the role this residual names.** The first draft said removal is detected anywhere but the tail; the second said the middle is detected and neither end. Both were measured against an attacker who *removes rows and stops*. Against one who can **write** — which is the same `aurora_migrator` every act on the list above requires — the chain is unkeyed `SHA256` over a canonical form this ADR publishes, so the suffix can simply be recomputed. Executed, on §5's chain of nine rows over three monthly partitions:

   | Act | Link-only verify | Anchored verify | A recorded head (`last_seq`, `last_hash`, `row_count`) |
   |---|---|---|---|
   | One row removed from inside a partition | `BROKEN at seq 6` | `BROKEN at seq 6` | — |
   | A **middle** partition dropped, nothing else | `BROKEN at seq 7` | `BROKEN at seq 7` | — |
   | The same drop **plus one `UPDATE` loop recomputing the suffix** | **`VERIFIES CLEAN`** | **`VERIFIES CLEAN`** | `last_hash` changes |
   | The **newest** partition dropped (tail) | `VERIFIES CLEAN` | `VERIFIES CLEAN` | detected: `last_seq` 9 → 6, `last_hash` changes |
   | The **oldest** partition dropped (prefix — what retention does) | `VERIFIES CLEAN` | `BROKEN at seq 4` | **not** detected: `last_seq` and `last_hash` **unchanged**; only `row_count` moves, 9 → 6 |

   So: **the chain detects accidental loss, storage corruption, and an actor who does not recompute. It does not detect a writing attacker, in the middle or at either end.** The recompute is one loop and needs nothing the attacker does not already have. What survives that loop, in this design as it stands, is the third column: a head recorded **outside** the tenant database moves when the newest rows go, whether or not the suffix was recomputed — and does not move for the prefix.

   Partitions are monthly ranges on `occurred_at` and the chain is ordered `(occurred_at, sequence)`, so dropping the **oldest** partition is **prefix** removal, and it is the one act that is both sanctioned and invisible to every mechanism here.

4. **What is not decided in this amendment.** Whether the chain should be **keyed** — an HMAC whose key is held outside the tenant database, so that a role with write access cannot recompute it — is the question the row above raises and **this amendment does not answer it**. It changes ADR-0028 §5's pinned construction, it interacts with key rotation, per-tenant key custody and `VerifyAsync`'s cost, and it belongs in a decision of its own. What is recorded here is only what is true without it, which is item 3.

5. **Anchoring, and why the prefix stays open regardless.** Anchoring the surviving first row to §5's 32 zero bytes catches prefix removal — executed, `BROKEN at seq 4` where the link-only verify reports clean — and is **incompatible with retention**: after one sanctioned drop of the oldest partition no surviving row carries the anchor, and the anchored verify fails forever after, indistinguishably from an attack. The chain head of `FOLLOWUP-026` does not see prefix removal either, because the head is the *newest* row. The only value that moves is the **row count**, and retention moves it too; separating them requires retention to publish the effect it expects to have on that count — **`FOLLOWUP-034`**'s second half, the project-manager's to schedule, not designed here. Note that a keyed chain would not close this one either: prefix removal leaves every surviving link valid under any key.

And one property of every check in this amendment, stated once and corrected from the first draft: **they are point-in-time, and the effect probe detects only an *unconditional* weakening.** A weakening keyed on session state — in the body, in a `WHEN` clause, in which function the trigger points at, or in any of the other compared columns — sixteen in `pg_trigger`, twenty-nine in `pg_proc` — is permanent, is invisible to the effect probe, and is why part 3 compares the whole row rather than the columns someone thought to list. A body replaced, used and restored between two runs is invisible to all three. Sampling cannot see a transient act, and never will; that is what a record kept outside the database is for, and it is `FOLLOWUP-033`'s question for the live-system half.

**The two stopping points compose, and the composite is a residual neither of them states alone.** Part 3 stops short of *the body is correct*, because the pin is taken from what the migration created; part 2 stops at *this session, now*. A migration that **ships** a session-conditioned guard body is past both at once, and all three parts are green on a system one `SET` from empty. Executed on the §3 shape, the condition written into the body the migration installs and the pin taken from it: `probed: 9, refused with 42501: 9, silent: (none)` · `triggers: 8, column comparisons: 360, findings: (none)` · `leaf_partitions 2, guarded_leaves 2, DEFAULT partitions 1` — then `SET aurora.maint = 'on'; DELETE FROM a.ev_09; TRUNCATE a.ev_default;` takes the trail from three rows to **zero**. This is the class the sibling review of PR #12 found live, and it is a **review and migration-authorship** question, not a check this clause can answer: every mechanism here compares the running system against what the migration created, so a defect present at creation is inside the reference. What bounds it is that part 3 pins the body's **definition** — `prosrc`, bound through `tgfoid` rather than by name — so the same body arriving **after** the migration is a difference on all eight guards, and the guard bodies are Full-tier review surface under `CLAUDE.md` for exactly this reason.

What would cover the tail half of the residual is **a chain head held outside the tenant database**: ADR-0018's daily job writing the head of each tenant's chain to `catalog.operator_audit_event`, where a shortened or restarted chain contradicts a head recorded yesterday — executed above, the head does move on tail removal. It needs two things that do not exist: the row that creates `catalog.operator_audit_event` (`../architecture/solution-layout.md` §6.4 item 5, carried as **`B-19`**) and a scheduler for platform jobs (**`FOLLOWUP-031`**, which ships `Aurora.Platform.Jobs`). It is therefore **named as the residual's partial cover, not written into this clause** — writing it in would repeat the exact defect this amendment exists to fix, a guarantee carried by unbuilt work — and it is carried as **`FOLLOWUP-026`**, whose scope is now the tail, not the prefix.

### Two directions considered and not taken, with the executed reason

- **Revoke `TRUNCATE` from the owning role.** It does bite — `REVOKE TRUNCATE ON <partition> FROM aurora_migrator` takes the owner's ACL entry from `arwdDxtm` to `arwdxtm` and the owner's `TRUNCATE` then returns `42501: permission denied for table`, executed. But the owner re-grants to itself in one statement: `GRANT TRUNCATE ON <partition> TO aurora_migrator`, **issued as `aurora_migrator`, no elevation**, and the next `TRUNCATE` returns `TRUNCATE TABLE`. Executed. So against the role this is aimed at it is a speed bump, and adopting it would put a second per-partition expectation into mechanism 1's exact-ACL comparison that has to be maintained in lockstep with the guard — the per-table memory this ADR exists to remove. It would also destroy the effect probe's discrimination: part 2 requires `42501` **as the owner**, and that is conclusive only because the owner's privilege path cannot produce `42501` — revoke `TRUNCATE` from the owner and a probe that reports green can no longer distinguish a working guard from a missing one behind a permission error. The half of the direction that is worth keeping is the *naming*, which is part 5 of the clause above: `TRUNCATE` belongs to `aurora_migrator` and to no one else, and mechanism 1 already executes that assertion.
- **A chain-head row inside the tenant database.** It is the only direction that survives a DDL-capable attacker — but only when the head sits somewhere that attacker cannot reach. Inside the tenant database it does not: the role that drops the guard rewrites the head in the same session. And a running head needs `UPDATE`, in the one schema whose entire premise (Options table, chosen row) is that every table in it is append-only, so it would either break mechanism 2's schema-wide `SELECT, INSERT` default or move the head to `platform`, where `aurora_app` can rewrite it without any DDL at all. Kept as the residual's cover in its out-of-database form, above.

### Two consequences worth stating rather than leaving accidental

- **The mandated `DEFAULT` partition closes the concurrent-detach window.** `ALTER TABLE … DETACH PARTITION CONCURRENTLY` is **refused outright while a `DEFAULT` partition exists** — executed: `ERROR: cannot detach partitions concurrently when a default partition exists`, and the same statement succeeds once the `DEFAULT` partition is dropped. Concurrent detach leaves a partition in a pending state, outside `pg_partition_tree` and therefore outside both probes, with its rows outside the parent. §3 mandates a `DEFAULT` partition for a different reason — routing rows that no month covers — and this is a second, independent reason to keep it. **It also means dropping the `DEFAULT` partition is a privilege escalation in disguise** — and §3's health check does not notice, because it asserts emptiness and not existence. Executed on the shape a developer naturally writes, an aggregate over the partitions that are `DEFAULT`: with the `DEFAULT` partition present and empty it prints `default partition holds 0 rows`; with the `DEFAULT` partition **dropped** it prints `default partition holds 0 rows`, because a sum over no rows is zero. The check must assert **exactly one `DEFAULT` partition exists** and then that it is empty, and report both numbers — executed, the corrected form fails with `expected exactly 1 DEFAULT partition, found 0`. An emptiness check that cannot tell "empty" from "absent" is the `CLAUDE.md` self-check #2 defect wearing a different hat, and here absence is the more dangerous of the two states.
- **What three reviewers tried against this clause and could not break**, recorded so a fourth does not spend the time again: `DROP TRIGGER` on a single leaf (the enumeration and the effect probe both catch it); a `SECURITY DEFINER` wrapper function calling the truncate; the guard function itself made `SECURITY DEFINER`; `ALTER FUNCTION … OWNER TO`; `ALWAYS` guards under `session_replication_role = 'replica'`; `TRUNCATE ONLY` on the parent, which PostgreSQL itself refuses (`cannot truncate only a partitioned table`), and the multi-table and `CASCADE` forms, refused by the guard with the guard's own error. The fifth review also checked the one assumption the population filter rests on: **a cloned trigger is `tgisinternal = false` on 17.11**, so the non-internal filter does include the clones, and `tgparentid` is what separates clone from local — had clones been internal, the specified filter would have re-created round 4's blocker. The bypasses that *did* work are every one named in this amendment, and each has a criterion or a written limitation attached to it.
